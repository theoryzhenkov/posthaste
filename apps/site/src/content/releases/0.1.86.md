## The runtime is now its own lean binary

Another internal-foundations release for split deployments: the app behaves
exactly as in 0.1.85 — the default bundled setup is unchanged. What landed is the
piece 0.1.83 pointed at: the runtime can now run as its own installable binary,
separate from the backend, carrying none of the backend's weight.

### Under the hood

- **A standalone runtime daemon.** There's now a runtime binary that connects to
  a remote backend and serves the same `/v1` API your clients already speak — so
  you could run the backend on one machine and a runtime in front of it on
  another, with several clients sharing that runtime. It builds *without* the mail
  store, the provider engine, or the IMAP code, because a runtime that reaches its
  backend over the network never needs them.
- **The `/v1` API became its own layer.** The whole client-facing surface — the
  REST endpoints and the live session/stream the app uses — moved into a crate
  that depends only on the runtime, not the backend. That's what lets the
  standalone runtime ship lean, and it keeps the client boundary in one place.
- **Real boundaries instead of compile flags.** An earlier attempt gated the
  backend code off with build flags, which left conditional cruft throughout the
  runtime. This release replaces that with clean crate boundaries — each binary
  links only what its role needs, and nothing is compiled in just to be switched
  off.
- The OAuth sign-in flow stays with the backend (it needs the provider machinery),
  so the bundled app is unchanged; a remote runtime simply doesn't offer it.
