# Runtime crate code patterns

## 1. Contract crate pattern

`crates/posthaste-runtime-contract` contains contract-only Rust types.

Allowed dependencies in this slice:

- `async-trait`
- `futures-util` for transport-neutral boxed runtime streams
- `posthaste-domain` for shared domain/runtime projection types such as `AppSettings`
- `serde`
- `serde_json`
- optional `utoipa` behind the `openapi` feature for generated API schemas

Pattern:

```rust
#[async_trait]
pub trait RuntimeCore: Send + Sync {
    async fn runtime_status(&self, caller: RuntimeCaller) -> Result<RuntimeStatus, RuntimeError>;
    async fn get_app_settings(&self, caller: RuntimeCaller) -> Result<AppSettings, RuntimeError>;
    async fn run_mutation(
        &self,
        caller: RuntimeCaller,
        request: MutationRequest,
    ) -> Result<MutationReceipt, RuntimeError>;
}
```

Keep transport and implementation types out of this crate. Do not add Axum, Tauri, provider-client, SQLite, store-row, or frontend dependencies here.

## 2. Identifier pattern

Runtime identifiers are opaque newtypes over strings:

```rust
#[derive(Clone, Debug, Eq, PartialEq, Hash, Serialize, Deserialize)]
#[serde(transparent)]
pub struct ViewId(String);
```

Expose `new` and `as_str`. Do not expose parsing helpers that infer account, provider, mailbox, message, or storage facts from identifier contents.

## 3. Authority builder test pattern

Authority runtime integration tests use fresh temp roots and a mock `SecretStore`:

```rust
let config = AuthorityRuntimeBuildConfig::new(
    root.join("config"),
    root.join("state"),
    root.join("cache"),
)
.with_secret_store(Arc::new(TestSecretStore));

let build = build_authority_runtime(config).await?;
```

Tests assert behavior through `RuntimeCore`, not through private fields:

```rust
let status = build.handle.runtime_status(RuntimeCaller::test()).await?;
```

Link tests to SPECial assertions with `// spec: path#assertion-id` comments immediately above the test.

## 4. Build assembly pattern

Authority runtime assembly follows this order in the first slice:

1. create state and cache roots
2. open TOML config repository
3. initialize defaults or import bootstrap config if the repository is empty
4. open SQLite store under `state_root/mail.sqlite`
5. build `MailService`
6. sync source projections
7. create event broadcast channel
8. build and start the authority-runtime `AccountSupervisor`
9. build `AuthorityRuntimeHandle`, `RuntimeShutdownHandle`, and initial `RuntimeStatus`

Do not start HTTP, create routers, bind sockets, create webviews, or read renderer state in this path.

## 5. Account mutation contract pattern

Account mutation request/result structs live in `posthaste-runtime-contract` when the same behavior must be callable from HTTP and future desktop/runtime adapters. They may contain shared domain types, but not Axum extractors, `utoipa` schema derives, or HTTP status concepts.

`posthaste-authority-runtime` owns the concrete side effects for these methods: config/service writes, secret-store writes, event append/broadcast, and account supervisor lifecycle/verification/reload/delete calls. Delete methods remove managed secrets, stop/remove the account runtime, delete config, and publish the account-delete event; adapters remain responsible only for transport-owned assets such as deleting an uploaded logo file after runtime account deletion succeeds.

## 6. Settings and smart-mailbox mutation contract pattern

Settings and smart-mailbox config mutation request/result structs live in `posthaste-runtime-contract` when the same behavior must be callable from HTTP and future runtime adapters. They may contain shared domain settings, rules, mailbox, and message-summary projection types, but not Axum extractors, `utoipa` schema derives, or HTTP status concepts.

`posthaste-authority-runtime` owns the concrete side effects for these methods: settings and smart-mailbox config writes, automation backfill checks, and config event append/broadcast. Adapters preserve transport response shaping after the runtime call.

## 7. OAuth materialization pattern

OAuth browser start/callback routes keep HTTP concerns in `posthaste-server`: request validation, pending-flow state, provider authorization-code exchange, redirect query handling, and success/processing HTML.

After token exchange, the adapter calls `AuthorityRuntimeHandle` for account materialization. Authority runtime encodes token sets, writes/replaces managed secrets, creates provider-first IMAP/SMTP OAuth accounts, patches existing accounts to OAuth2, publishes account events, and starts/restarts account lifecycle through the supervisor.

Keep OAuth callback materialization out of direct `AppState.service`, `AppState.secret_store`, and `AppState.supervisor` access once these handle methods exist.

## 8. Error pattern

Build-time failures use typed errors in `AuthorityRuntimeBuildError`.

Runtime-call failures use the adapter-safe `RuntimeError(RuntimeAdapterError)` envelope from the contract crate. Do not return transport response types from runtime methods.

## 9. API bridge pattern

`AuthorityRuntimeBuild::api_bridge` exposes existing service/store/secret/event handles only for compatibility harnesses and migration constructors. `AuthorityRuntimeCore` owns explicit service/store/event dependencies and must not call through `api_bridge` internally.

Keep this bridge out of renderer and desktop code. Do not add new behavior to the bridge; add behavior to `RuntimeCore` or `AuthorityRuntimeHandle` and let adapters call that path.

## 10. Live account runtime provider pattern

Live provider-backed reads use `LiveAccountRuntimeProvider` while supervisor ownership is moving:

```rust
let gateway = self.core.live_accounts.gateway(&account_id).await?;
```

The provider trait and concrete `AccountSupervisor` belong to `posthaste-authority-runtime`; `posthaste-server::supervisor` is only a compatibility re-export. New HTTP handlers should not call the supervisor directly once a runtime method exists.

## 11. Message operation and query pattern

Runtime contract message methods use domain command/request payloads and return domain command results or adapter-safe byte payloads. Mail-list/search reads use `MailQueryRequest { query, presentation, visibility }` and return `MailQueryPage`. The query string is the universal selector: `in:Inbox` resolves to a saved smart mailbox, `in:Account/` resolves to a concrete source, `in:Account/Archive` resolves to a concrete source mailbox, and `conversation:<id>` selects messages in a derived conversation. `MailPresentationRequest::CollapsedByConversation` is a backend grouping presentation, not a canonical conversation object.

Authority runtime implementations perform provider gateway lookup internally through `LiveAccountRuntimeProvider`, own query parsing/evaluation and saved-query expansion, record search/cache visibility as part of query execution, trigger cache maintenance, and publish emitted domain events through the runtime bridge event sender.

Adapters preserve transport response shaping (JSON envelope, headers, sanitization) after the runtime call.

## 12. Event stream pattern

Runtime event methods keep the contract transport-neutral by returning domain events, not SSE frames:

```rust
let subscription = runtime
    .subscribe_events(RuntimeCaller::api(), filter)
    .await?;
```

`RuntimeCore::subscribe_events` owns the durable replay query and the live broadcast receiver. It subscribes before querying backlog, returns `RuntimeEventSubscription { replay, live }`, and filters both replay and live events with `EventFilter`. Adapters may chain `replay` and `live`, but should only convert each `DomainEvent` into the adapter wire format.

## 13. Runtime session stream pattern

`RuntimeCore` session methods keep renderer state delivery behind one session cursor:

```rust
let session = runtime.open_session(caller).await?;
let snapshot = runtime
    .open_session_view(caller, session.session_id.clone(), descriptor)
    .await?;
let frames = runtime
    .subscribe_runtime_frames(caller, session.session_id, Some(RuntimeSessionSeq::new(0)))
    .await?;
```

Authority runtime generates opaque session ids, stores active session views, and forwards `ViewFrame` updates as `RuntimeFrame::ViewSnapshot` or `RuntimeFrame::ViewReplace`. Adapters serialize `RuntimeFrame` values and use `RuntimeSessionSeq` as the SSE id or native resume cursor. Reconnect handling collapses stale history to current snapshots for open views.

## 14. Runtime mutation pattern

Session-scoped mutations use the shared `MutationRequest` and `MutationReceipt` contract:

```rust
let receipt = runtime
    .run_mutation(caller, request)
    .await?;
```

The authority runtime validates the session/account scope before accepting the mutation, assigns a `RuntimeMutationId`, emits `RuntimeFrame::MutationSettlement` frames on the same session stream, and records the latest settlement for collapsed reconnect. It routes the message-action catalog (setKeywords, setReadState, setFlaggedState, setUserTags, moveToMailbox, moveToRole, archive, trash, restoreToInbox, destroy) through one accept -> execute -> settle helper to the existing handle actions; durable idempotency records for restart-safe send-class mutations remain a later coordinator slice.

## 15. Shutdown and readiness gate pattern

Runtime shutdown is owned by `RuntimeShutdownHandle`.

The first implementation has no extracted account tasks to drain, so shutdown only marks lifecycle state as stopped. Future task owners should attach to this handle rather than letting server or desktop adapters stop provider connections directly.

`AuthorityRuntimeHandle::runtime_status` is always callable. Every other `RuntimeCore` method checks lifecycle liveness before reading stores, using live providers, or applying mutations. The liveness gate allows `Ready` and `Degraded`; it rejects `Starting`, `Stopping`, and `Stopped` with `RuntimeNotReady` and lifecycle details. The mutation-service availability gate (`account_mutations`) remains separate so migration handles can distinguish "runtime stopped" from "mutation runtime is not wired".

| api-bridge-not-runtime-contract          | MUST | `api_bridge` is not used as a permanent runtime contract, as an internal runtime-core dependency bag, or by renderer/desktop code.                                                                                                       |
| account-mutation-contract-pattern        | MUST | Account mutation contracts stay transport-neutral and concrete side effects live in authority runtime methods.                                                                                                                           |
| settings-smart-mutation-contract-pattern | MUST | Settings and smart-mailbox config mutation contracts stay transport-neutral and concrete side effects live in authority runtime methods.                                                                                                 |
