# Runtime extraction implementation decisions

## 1. First-slice scope

The first implementation slice establishes the runtime crate seam required before server and desktop adapters can share mail behavior.

It creates two crates using the names recommended by the L2 runtime and backend specs:

- `crates/posthaste-runtime-contract`
- `crates/posthaste-authority-runtime`

This slice does not use the temporary single-crate fallback.

## 2. Shared runtime contract

`posthaste-runtime-contract` owns adapter-safe runtime types and the first `RuntimeCore` trait.

Concrete choices:

- `RuntimeCore` is an async trait so future view, mutation, event, and resource methods can perform runtime work without changing trait style.
- The first method is `runtime_status(RuntimeCaller) -> RuntimeStatus` because the test-plan seam requires building an authority handle and reading startup/runtime status.
- The first API-backed read method is `get_app_settings(RuntimeCaller) -> AppSettings`, used by `GET /v1/settings` to prove a low-risk handler can call the runtime handle.
- Account/config read methods are grouped behind an authority-runtime account read service that owns account overview construction and `AccountScopeRequest` resolution.
- Provider-backed reads use runtime contract methods and a `LiveAccountRuntimeProvider` seam; concrete account supervisor/gateway ownership now lives in `posthaste-authority-runtime`.
- Account CRUD/lifecycle/reload/delete mutations use adapter-neutral runtime contract payloads (`CreateAccountMutation`, `PatchAccountMutation`, and secret/transport mutation structs) so HTTP schemas can adapt to a transport-free authority method.
- Settings patch, automation preview, and smart-mailbox create/patch/delete/reset use adapter-neutral runtime contract payloads so config writes, automation backfill checks, and config event publication live in authority runtime instead of HTTP handlers.
- OAuth callback account materialization uses authority-runtime handle methods for token-set encoding, secret writes, account create/patch, and supervisor lifecycle while HTTP redirect/query/HTML behavior remains in `posthaste-server`.
- Event replay and live subscription use runtime contract methods. The runtime accepts the shared `EventFilter`, queries durable backlog, subscribes to the runtime broadcast channel before replaying backlog, filters live events, and suppresses live sequences already covered by replay.
- Mail-list/search reads use `query_mail_page` with query text and presentation options instead of route-shaped runtime methods. Saved smart mailboxes are expanded by `in:<name-or-id>`; source mailboxes use `in:<account>/<mailbox>`; opened conversations use `conversation:<id>`.
- Runtime IDs are opaque string newtypes: `RuntimeSessionId`, `ViewId`, `SubscriptionId`, `ClientMutationId`, and `RuntimeMutationId`.
- Runtime revisions use numeric `ViewRevision` and `RuntimeSessionSeq` newtypes.
- Runtime view frames (`ViewFrame`) remain available for the per-view bridge, while `RuntimeFrame` is the session-scoped renderer stream envelope for view snapshots/replacements, view closure, mutation settlement, notifications, and heartbeats.
- Mail-list runtime views use `ViewDescriptor { family: "mailList" }`, `MailQueryRequest`, and `MailListViewState` snapshots so keyword updates can publish full replacement snapshots instead of renderer-applied patches.
- Contract payloads serialize with camelCase fields unless the spec requires another convention.
- The adapter error envelope is `RuntimeAdapterError { code, message, retryable, correlationId, details }` with the initial code catalog from `docs/runtime/L2.md`.

The contract crate must not depend on Axum, Tauri, React/frontend packages, provider clients, SQLite table types, or replica-table types.

## 3. Authority runtime builder

`posthaste-authority-runtime` exposes `build_authority_runtime(AuthorityRuntimeBuildConfig) -> AuthorityRuntimeBuild`.

Concrete choices:

- `AuthorityRuntimeBuildConfig` accepts already resolved `config_root`, `state_root`, and `cache_root` paths.
- Empty config roots are initialized with default config and smart mailboxes, or imported from `bootstrap_path` when supplied.
- The builder opens `DatabaseStore` at `state_root/mail.sqlite` and uses `state_root` as the store data root.
- The builder constructs `MailService`, syncs source projections, creates a runtime event broadcast channel, and records the configured account count in startup status.
- Production callers can use the default `SystemSecretStore`; tests can pass an injected `SecretStore` implementation for the mock-secret-store seam required by the test plan.
- The build output is `AuthorityRuntimeBuild { handle, shutdown, runtime_status }`.

The builder is transport-free: it does not bind a listener, build an Axum router, create Tauri windows, or expose transport handles in runtime method signatures.

## 4. Runtime status and shutdown seam

`RuntimeStatus` intentionally reports only adapter-safe readiness fields:

- lifecycle state
- config/store/cache readiness booleans
- configured account count

It does not expose filesystem roots, provider secrets, bearer tokens, SQLite handles, or keyring references.

`RuntimeShutdownHandle` is present in the first slice even though account runtimes, view subscriptions, and queued mutation workers are not extracted yet. The handle marks the runtime stopped so adapters and tests depend on the runtime-owned shutdown seam from the beginning.

`runtime_status` remains readable after shutdown and reports `Stopped`. Other runtime operations check lifecycle liveness first and return `RuntimeNotReady` when the runtime is `Starting`, `Stopping`, or `Stopped`. Optional migration-service availability remains a separate gate so an active test/migration handle without mutation services can report that condition distinctly from lifecycle shutdown.

## 5. API migration bridge

The second slice starts the API adapter wrapping step. `AuthorityRuntimeBuild` exposes a temporary `api_bridge` containing the existing service/store/secret/event parts for compatibility harnesses and migration constructors. Runtime internals own explicit service/store/event dependencies rather than using `api_bridge` as a dependency bag, and `posthaste-server::AppState` exposes only the runtime handle plus HTTP-adapter state.

This bridge is not a new public mail behavior contract. It is controlled by `docs/eph/PLAN-L3-api-runtime-wrapper-migration.md` and must disappear when compatibility harnesses no longer need direct seeding handles.

## 6. Deferred extraction

The following remain outside the current slices and should be implemented through later L2 test-plan sections:

- remaining OAuth browser session HTTP route cleanup beyond callback account materialization
- remaining direct API handler service/store access for behavior that has not yet moved to runtime methods; account logo bytes/static files intentionally remain server-owned while account logo metadata and account deletion resource linkage are runtime-owned
- remaining renderer migration from legacy domain-event refetch paths to the session-scoped `RuntimeFrame` stream beyond the mail-list keyword slice
- mutation coordinator and durable idempotency records
- runtime resource resolver and scoped resource capabilities

## 7. Assertions

| ID | Sev. | Assertion |
| --- | --- | --- |
| runtime-contract-crate-name | MUST | The first runtime contract crate is `posthaste-runtime-contract`, not a module inside `posthaste-server`. |
| authority-runtime-crate-name | MUST | The first authority runtime crate is `posthaste-authority-runtime`, not a module inside `posthaste-server`. |
| status-first-runtime-core-method | MUST | The first `RuntimeCore` method reads runtime status through adapter-neutral `RuntimeCaller`. |
| settings-first-runtime-read | MUST | `get_app_settings` is the first API read moved behind `RuntimeCore`. |
| account-read-service-scope | MUST | Account/config reads use a runtime-owned account read service and `AccountScopeRequest` for default enabled-account scope. |
| live-account-runtime-provider-seam | MUST | Live provider-backed reads use a runtime-owned provider seam, backed by the authority-runtime account supervisor. |
| account-mutation-contracts | MUST | Account CRUD/lifecycle/reload/delete mutations use transport-neutral runtime contract request/result types rather than Axum request types. |
| settings-smart-mutation-contracts | MUST | Settings patch, automation preview, and smart-mailbox config mutations use transport-neutral runtime contract request/result types rather than Axum request types. |
| account-resource-linkage-runtime-owned | MUST | Runtime account mutation methods own account delete resource linkage, including managed secret deletion, supervisor removal, config deletion, and account event publication. |
| oauth-materialization-runtime-owned | MUST | OAuth callback token-set persistence and provider-first account materialization are owned by authority-runtime handle methods; adapters keep redirect/query/HTML shaping. |
| builder-roots-pre-resolved | MUST | Authority runtime build inputs receive pre-resolved config, state, and cache roots. |
| status-no-sensitive-fields | MUST | Runtime status does not expose filesystem roots, provider secrets, bearer tokens, SQLite handles, or keyring references. |
| api-bridge-temporary | MUST | `AuthorityRuntimeBuild::api_bridge` is a compatibility-harness and migration-constructor bridge, not a permanent runtime contract or runtime-core dependency bag. |
| message-mutation-runtime-contract | MUST | The runtime contract exposes named methods for message send, message mutations, detail, and attachment bytes, and one `query_mail_page` method for mail-list/search reads. Adapters must not own provider gateway lookup, query evaluation, cache-maintenance triggers, or event publication for those operations. |
| event-subscription-runtime-backed | MUST | Event backlog replay and live broadcast subscription are runtime-owned; adapters map returned domain events to their transport wire shape. |
