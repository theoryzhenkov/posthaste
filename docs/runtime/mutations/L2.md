## 1. Undo/redo stack

Undo is runtime-backed. The renderer may expose undo/redo UI and shortcuts, but
the runtime owns the history: it records an **invertible change-diff** for each
reversible message mutation, keeps a per-session seq-ordered **undo/redo stack**,
and broadcasts the current stack tops on the session stream. The renderer holds
no before-images or replay logic. The stack behaves like a desktop editor's:

- Each reversible message mutation (keyword/mailbox changes) is captured as a
  diff `{ keywords: { added, removed }, mailboxes: { added, removed } }`
  after the provider confirms the forward mutation. The diff is pushed onto the
  per-session undo history and **clears the redo history**. Non-invertible mutations
  (e.g. `message.destroy`) are not recorded.
- The runtime emits a `mutationHistory` frame (`{ canUndo, canRedo, undoTop?, redoTop? }`)
  whenever the history changes. `undoTop` / `redoTop` are the current stack tops:
  each carries the message id, source id, the session seq at which the diff was
  captured, and the invertible diff itself.
- To **undo**, the renderer sends `message.applyDiff` with `inverse(diff)` and
  `undoOf: seq`. To **redo**, it sends `message.applyDiff` with the original
  `diff` and `redoOf: seq`. These are ordinary optimistic message mutations:
  they enter the client outbox, fold through the same replay guard as any user
  action, and settle through the same provider path as the forward mutation.
  Under last-writer-wins, the runtime navigates its local history pointer
  without re-recording a new diff for the undo/redo action itself.
- The stack is per session and bounded; the oldest step is evicted past the bound.

Undo/redo mutations flow through the same accept → execute → settle path (and the
same outbox) as the forward mutation, so they are offline-capable and converge
identically. Because the renderer sends a concrete diff mutation, idempotent retry
of an undo/redo invocation is handled by the normal mutation idempotency
machinery rather than by stack navigation.
guaranteed, since these navigate stack position rather than addressing a specific
mutation id.

## 2. Settlement and reconciliation

### 2.1 Settlement states

The catalog uses the settlement states defined by the adapter ([adapter L1 §5](../adapter/L1.md)):
`accepted`, `localApplied`, `queued`, `confirmed`, `failed`, `conflict`.

`confirmed` means the **confirmation watermark has passed the mutation** — an
authoritative assertion whose `after` reflects it has been applied to the
projection — at which point the pending overlay entry retires. It does not mean
only that a provider command returned. A mutation with no provider work may move
`accepted` → `localApplied` → `confirmed` in one runtime turn; a mutation with
provider work may stay `queued` while offline or retrying. An entity-creating
mutation (draft create, send) reconciles its provisional id to the
provider-assigned id and retires by identity once a projection row with that id
exists ([replication L1 §5.4](../../replication/L1.md)).

### 2.2 Reconciliation failures

If provider reconciliation fails transiently, the mutation stays pending and the
local effect stays folded; it retries on the next connectivity window. On
permanent rejection the runtime settles the mutation `failed`, drops the pending
overlay entry so the view reverts to authoritative state, and surfaces the
failure. A mutation accepted by the provider but never confirmed is retired after
a bounded number of convergence cycles and recorded for telemetry, so the pending
overlay cannot grow unbounded ([replication L1 §9](../../replication/L1.md)). The
UI renders settlement state and may offer user actions, but it does not own
conflict resolution.

## 3. The run_mutation pattern

Session-scoped mutations use the shared `MutationRequest`/`MutationReceipt`
contract:

```rust
let receipt = runtime.run_mutation(caller, request).await?;
```

The authority runtime validates the session/account scope before accepting,
assigns a `RuntimeMutationId`, emits `RuntimeFrame::MutationSettlement` frames on
the same session stream, and records the latest settlement for collapsed reconnect.
It routes the message-action catalog (`setKeywords`, `setReadState`,
`setFlaggedState`, `setUserTags`, `moveToMailbox`, `moveToRole`, `archive`,
`trash`, `restoreToInbox`, `destroy`) through one accept → execute → settle helper
to the handle actions; role moves are resolved runtime-side. Account mutation
methods own their delete resource linkage ([internals L3 §1](../internals/L3.md),
`account-mutation-contract-pattern`); drafts and send remain dedicated methods.

## 4. Validation

### 4.1 Provider-latency tests

Tests cover provider command delay/failure while local view state updates
immediately according to the mutation contract.

### 4.2 Mutation catalog tests

Tests cover read/flag/tag, role move, destroy, draft save, send, settings/account,
retry, undo, and conflict-resolution mutations at the runtime boundary. Send tests
cover crash/retry idempotency before provider submission so duplicate sends cannot
occur from a reused `clientMutationId`.

## 5. Assertions

| ID | Sev. | Assertion |
| --- | --- | --- |
| retire-on-confirmation | MUST | A pending mutation's optimistic effect is retired when the confirmation watermark passes it (an authoritative assertion reflects it), not when its provider command returned. |
| entity-convergence-by-id | MUST | Entity-creating mutations reconcile a provisional id to the provider id and retire by identity once a projection row with that id exists. |
| provider-failure-settlement | MUST | Provider reconciliation failures settle through runtime state, not UI-owned conflict logic. |
| undo-stack-runtime-owned | MUST | The undo/redo stack is per-session runtime state; the runtime records an invertible change-diff after provider confirmation and the renderer holds no before-images or replay logic. Undo/redo execute as ordinary `message.applyDiff` mutations. |
| mutation-settlement-on-session-stream | MUST | `run_mutation` assigns a `RuntimeMutationId` and emits settlement frames on the same session stream, recording the latest settlement for collapsed reconnect. |
