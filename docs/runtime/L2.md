## 1. Implementation boundary

### 1.1 Contract

The bundled application is a desktop host, packaged renderer, and embedded authority runtime shipped as one app.

Implementation may split across Rust crates, Tauri commands, local channels, and optional loopback HTTP. Those layers must preserve the runtime contract: the UI sends typed scopes/actions and receives runtime-produced state.

The bundled application is not a web renderer pointed at an external daemon. A loopback API may exist, but the deployment mode is defined by the embedded authority runtime.

## 2. Runtime components

### 2.1 Component map

The bundled authority runtime contains:

- desktop host and window manager
- config repository
- secret resolver
- SQLite store and migrations
- provider supervisor and account runtimes
- domain service
- query/view service
- mutation coordinator
- event log and event bus
- body/blob cache service
- UI session registry
- runtime adapter for renderer calls and state streams
- optional `/v1` API adapter for tools, tests, debugging, and migration bridges

### 2.2 Shared state types

Runtime adapters use shared mail state types: `QueryScope`, query-window state, `MessageSummaryState`, `MessageDetailState`, `ConversationRef`, body and attachment tokens, named mutations, mutation settlement state, and state assertions.

The UI adapter must not define parallel mail DTOs unless it is a generated or mechanical projection of the shared types.

## 3. Bundled application package

### 3.1 Package contents

The production bundle contains:

- the Tauri desktop executable
- static renderer assets built from the web application
- Rust authority runtime code and provider drivers
- schema migrations and local runtime resources
- platform secret-store integration
- optional API/contract artifacts for local inspection and generated-client checks

The bundle must be able to open existing local state without `posthaste serve` or another separately installed backend process.

### 3.2 Production renderer source

Production bundled mode loads renderer assets from the application bundle. Remote renderer code is not part of this deployment mode.

The renderer may fetch remote mail content only through runtime-owned provider flows. It does not load the app shell from a hosted web origin.

### 3.3 Development renderer source

Development builds may load renderer assets from a local Vite server. The development server serves JavaScript and static assets only; it is not the mail authority.

Development and production use the same runtime adapter contract. A bug that reproduces only because development bypasses the runtime contract is a deployment-mode bug.

## 4. Startup and lifecycle

### 4.1 Startup sequence

Bundled startup follows this shape:

```text
resolve platform paths
 -> initialize observability
 -> open config repository
 -> open secret backend
 -> open SQLite store and run migrations
 -> build authority runtime handle
 -> start event bus and account supervisor
 -> register renderer runtime adapter
 -> open main renderer window
```

The renderer can show startup progress, but it must not issue mail reads before the runtime adapter reports readiness.

### 4.2 Startup failures

Failure to open required local dependencies is a startup error with a user-visible diagnostic. Examples include an unreadable state directory, failed database migration, or unavailable required secret backend.

Account-specific provider failures become account runtime status when possible. They should not block the renderer from opening existing local mail state.

### 4.3 Shutdown

Application shutdown stops UI sessions, stops account runtimes, flushes durable local state, closes provider connections, and leaves queued provider work recoverable on the next launch.

Bundled mode does not leave a hidden authority daemon running after application exit unless the user explicitly starts a separate daemon deployment mode.

## 5. Runtime handle and adapters

### 5.1 Authority runtime handle

Implementation should expose one authority runtime handle that is independent of Axum and Tauri transport details. The handle owns or references the service, store, supervisor, view registry, mutation coordinator, event bus, and body/blob cache.

Transport code calls the handle. Mail behavior must not be implemented separately in the Axum router and the Tauri adapter.

### 5.2 API adapter

The `/v1` router is an adapter over the same authority runtime handle. It remains useful for MCP, scripts, tests, debugging, external clients, and migration work.

The router may be mounted on a loopback listener in bundled mode, but renderer components do not depend directly on route handlers when a runtime adapter operation exists.

### 5.3 Renderer runtime adapter

The renderer runtime adapter maps typed UI operations to runtime handle calls and streams runtime state changes back to webviews.

The adapter contract is semantic, not a mandate for exact Tauri command names. Implementations may split a stream across commands and events, but the TypeScript side exposes one facade with the operations in this section.

### 5.4 Adapter identifiers

Runtime adapter payloads use opaque identifiers:

| Identifier | Owner | Purpose |
| --- | --- | --- |
| `RuntimeSessionId` | Runtime | One renderer connection. |
| `ViewId` | Runtime | One runtime-owned view opened by a session. |
| `ViewRevision` | Runtime | Monotonic revision for one view. |
| `SubscriptionId` | Runtime or adapter | One active state stream subscription. |
| `ClientMutationId` | Renderer | Stable idempotency key for a user-submitted mutation. |
| `RuntimeMutationId` | Runtime | Runtime settlement identity for an accepted mutation. |

The renderer may store these identifiers for the lifetime of a window or component tree. It must not infer account, message, provider, or storage facts from their format.

### 5.5 Session operations

A renderer session starts before it opens mail views:

```text
connectRenderer(init) -> RendererSession
subscribeRuntime(sessionId, afterSeq?) -> runtime event frames
closeRenderer(sessionId)
```

`init` includes the window label, app version/build metadata when available, and renderer capabilities such as whether the window can open focused surfaces or download files. The runtime returns `RuntimeSessionId`, startup status, account status summaries, and adapter capability flags.

`subscribeRuntime` carries account status, sync status, mutation settlement, global errors, and optional event-sequence catch-up for the session. Mail list rows and message detail payloads still flow through view subscriptions.

### 5.6 View operations

The renderer opens views with serializable descriptors:

```text
openView(sessionId, descriptor, options?) -> ViewSnapshot
subscribeView(sessionId, viewId, afterRevision?) -> view frames
updateView(sessionId, viewId, descriptor | windowRequest) -> ViewSnapshot
closeView(sessionId, viewId)
```

`openView` returns the initial snapshot or a loading snapshot before asynchronous work continues. `subscribeView` sends a full snapshot when the supplied revision is absent, unknown, or too old. Ordinary updates are replacement frames, not renderer-applied patches.

`updateView` is used for query text changes, sort changes, window-extension requests, focused-message changes, and settings-surface target changes. It preserves the `ViewId` only when the runtime can treat the change as the same logical view.

### 5.7 View descriptors

The initial bundled adapter supports these descriptor families:

| Descriptor | Required identity | Runtime-owned state |
| --- | --- | --- |
| `mailList` | `QueryScope`, projection kind, sort/window request | Message or conversation rows, cursors, pending row markers, loading/error affordances. |
| `messageDetail` | account/source id and message id | Detail projection, body alternatives, attachments, body/attachment token state. |
| `conversation` | conversation id and optional token | Conversation envelope or view for the requested token. |
| `compose` | draft id or compose intent | Draft state, recipients, body, attachments, send readiness, save/send pending state. |
| `settings` | settings surface descriptor | Settings/account/smart-mailbox/source-mailbox state and edit settlement. |
| `accountStatus` | account id or all accounts | Runtime status, sync progress, provider errors, queued work. |

A descriptor is declarative. Components describe the state they need; they do not pass partially loaded messages for the runtime to repair.

### 5.8 View snapshot shape

Every view snapshot has a common envelope:

```text
ViewSnapshot {
  viewId,
  descriptor,
  revision,
  lifecycle,
  readWatermark,
  coverage,
  data,
  pendingMutations,
  error
}
```

`lifecycle` is a UI affordance supplied by the runtime: `loading`, `ready`, `updating`, or `error`. It is not a local-replica certainty model. `readWatermark` identifies the runtime state sequence or store read watermark used to produce the data when available.

`readWatermark` is not interpreted by renderer components for freshness. The runtime may use it for resume, diagnostics, query-window requests, or coverage proof construction.

`coverage` is the forward-compatible coverage seam. In bundled authority mode it asserts that the returned finite view state is complete for its descriptor, window request, and read watermark. A future replica runtime may replace that authority assertion with structural coverage, gap, and freshness data without making the renderer evaluate mail queries locally.

For `mailList`, `data` contains rows, cursor/window continuation state, total/known-count metadata when available, and row-level pending markers. For `messageDetail` and `conversation`, `data` contains the runtime projection plus token metadata. For `compose` and `settings`, `data` contains editable runtime state and any pending settlement fields.

### 5.9 Mail-list data shape

A `mailList` snapshot uses `MailListViewState`:

```text
MailListViewState {
  scope,
  projectionKind,
  sort,
  windowRequest,
  rows,
  continuation,
  readWatermark,
  coverage,
  knownTotalCount,
  pendingMutations,
  anchor
}
```

Rows use `MailListRowState`:

```text
MailListRowState {
  rowKey,
  resourceRef,
  projection,
  sortKey,
  orderKey,
  pendingMarkers
}
```

`projectionKind` is `message` or `conversation` for the first bundled implementation. `projection` is the runtime-produced row display state: a `MessageSummaryState` for message rows or a conversation row/envelope projection for conversation rows.

`continuation` carries opaque `beforeCursor` and `afterCursor` values plus `hasBefore` and `hasAfter`. `anchor` reports whether a requested anchor row was kept, moved, removed, or unknown.

### 5.10 View frames

View subscriptions emit full-state frames:

| Frame | Meaning |
| --- | --- |
| `view.snapshot` | Complete current view state. Sent on subscribe and resume fallback. |
| `view.replace` | Complete replacement for a newer `ViewRevision`. |
| `view.error` | Runtime could not produce the view state. Carries adapter error shape. |
| `view.closed` | Runtime closed or released the view. |

The first implementation should prefer full replacement frames over row patches. Row patch frames may be added later only if they remain runtime-authored and the full replacement path remains available.

### 5.11 Mutation operations

Mutations use one request shape:

```text
runMutation(sessionId, name, args, clientMutationId, context?) -> MutationReceipt
```

`name` is a catalogued mutation name. `args` are mutation-specific. `clientMutationId` is generated by the renderer and reused on retry of the same user intent. `context` may include the originating `ViewId`, expected `ViewRevision`, selected rows, or UI command source for diagnostics, but correctness cannot depend on private component state.

The receipt means the runtime accepted or rejected the submission. Observable mail changes arrive as view frames and runtime mutation-settlement frames.

When the runtime accepts a mutation, it persists the `clientMutationId` to `RuntimeMutationId` mapping before applying local effects or sending provider commands. Retrying the same user intent after a renderer reload or app restart returns the existing mutation record or settled result. This is required for send-class mutations, where double application can send duplicate mail.

### 5.12 Mutation settlement frames

The runtime reports mutation progress with settlement frames:

| State | Meaning |
| --- | --- |
| `accepted` | The runtime accepted the mutation id and will process it or report failure. |
| `localApplied` | The local runtime effect has been applied and affected views have been updated or are updating. |
| `queued` | Provider reconciliation is waiting for connectivity, retry, or background work. |
| `confirmed` | Provider reconciliation or local-only completion has confirmed the mutation. |
| `failed` | The runtime could not complete the mutation and has settled visible state. |
| `conflict` | User input is needed to choose a runtime-provided resolution. |

Not every mutation passes through every state. The UI renders these states but does not maintain a separate outbox or replay log.

Settlement frames are delivered to the submitting session and to sessions with active views that reference the `RuntimeMutationId` in their pending state. Other sessions receive ordinary view updates when the mutation affects their views; they do not need every settlement frame.

A conflict frame includes runtime-provided resolution options. The user's choice is submitted as another named mutation, carrying the original `RuntimeMutationId` or conflict token in its args. The renderer chooses among options; the runtime performs the resolution and settlement.

### 5.13 Resource operations

Attachment bytes, message source downloads, and other binary resources are runtime resources, not provider URLs exposed to the renderer.

The adapter may return bytes directly, a Tauri resource handle, or a short-lived local capability URL. Capability URLs are scoped to the local session, expire, and do not carry provider credentials.

### 5.14 Adapter error shape

Adapter calls and frames use a stable error envelope:

```text
RuntimeAdapterError {
  code,
  message,
  retryable,
  correlationId,
  details
}
```

Initial codes are `runtime_not_ready`, `invalid_descriptor`, `invalid_mutation`, `unauthorized`, `not_found`, `provider_unavailable`, `conflict`, `transport_disconnected`, and `internal`. `message` is safe for UI display only when the runtime marks it as such in `details` or the code definition allows it.

### 5.15 Loopback migration bridge

A protected loopback HTTP bridge may be used while extracting the runtime handle and renderer adapter. If it is used, the direct HTTP dependency stays inside the client runtime adapter module.

The bridge is temporary from the renderer's point of view. Components still target view subscriptions and named mutations, not ad hoc API fetches.

### 5.16 Rust contract and implementation crates

The runtime contract should be separate from the authority implementation so the bundled desktop app can embed the authority runtime now and future deployments can embed a replica runtime later.

Recommended crate shape:

```text
posthaste-runtime-contract
  RuntimeCore trait or equivalent facade contract
  caller context, sessions, views, frames, coverage, mutations, resources, errors

posthaste-authority-runtime
  AuthorityRuntimeHandle implements RuntimeCore
  RuntimeBuildConfig and RuntimeBuild output
  RuntimeShutdownHandle
  view service, mutation coordinator, resource resolver
  assembly of config, secrets, SQLite store, domain service, event bus, supervisor

future: posthaste-replica-runtime
  ReplicaRuntimeHandle implements RuntimeCore
  local replica, outbox, coverage/gap state, remote-authority sync
```

A temporary single crate is acceptable only if the public contract module stays free of authority-only dependencies and can later move without changing renderer/API adapter semantics.

### 5.17 Authority runtime handle shape

The authority runtime implementation should split transport-neutral runtime code from adapter code with a shape like:

```text
AuthorityRuntimeHandle
  cloneable implementation of RuntimeCore
AuthorityRuntimeCore
  config repository
  secret store
  SQLite store
  domain service
  account supervisor
  event bus/history
  query/view service
  mutation coordinator
  resource resolver
RuntimeShutdownHandle
  graceful shutdown and task joins
```

Names may change, but the seam must remain: Axum and Tauri adapters call the same runtime contract instead of rebuilding service/store/supervisor state.

### 5.18 Build inputs and outputs

The authority runtime builder accepts transport-neutral inputs:

```text
AuthorityRuntimeBuildConfig {
  configRoot,
  stateRoot,
  cacheRoot,
  bootstrapPath,
  processSettings,
  adapterCapabilities
}
```

It returns:

```text
AuthorityRuntimeBuild {
  handle,
  shutdown,
  runtimeStatus,
  apiAuthMaterial?,
  logGuard?
}
```

`apiAuthMaterial` is optional because a pure in-process adapter may not need bearer-token material. When a loopback or daemon API is enabled, the API adapter uses this material to protect `/v1`. The renderer adapter must not receive provider secrets.

### 5.19 Adapter-neutral caller context

Runtime handle methods receive an adapter-neutral caller context:

```text
RuntimeCaller {
  sessionId?,
  capabilities,
  accountScope?,
  operationSource,
  correlationId
}
```

Adapters authenticate and translate transport identity into this context. The runtime uses it for authorization, diagnostics, mutation attribution, and settlement routing. The handle must not depend on HTTP headers, Tauri window labels, or React component state for authorization decisions.

### 5.20 Runtime API groups

The shared runtime contract exposes these method groups:

| Group | Purpose |
| --- | --- |
| Lifecycle | Start enabled accounts, reload config, report status, and shut down gracefully. |
| Reads | Return local runtime/API projections for settings, accounts, mailboxes, smart mailboxes, tags, messages, conversations, and query pages. |
| Views | Connect renderer sessions, open/update/close views, and subscribe to view frames. |
| Mutations | Run named mutations, inspect mutation state, retry, undo, and resolve conflicts. |
| Events | Subscribe to runtime events and read event history for API catch-up/snapshot. |
| Resources | Resolve body, attachment, and source resources into bytes, handles, or scoped capability URLs. |

The first authority implementation may route some read and command methods through existing service functions while the view and mutation services are extracted. The method still belongs to the runtime contract; adapters should not reach around the handle to private service/store fields.

### 5.21 Adapter boundaries

The Axum adapter owns HTTP concerns: extraction, auth middleware, host/origin checks, status codes, API error JSON, OpenAPI/AsyncAPI artifacts, CORS, and optional static app serving.

The Tauri adapter owns desktop concerns: command names, event emission, window/session labels, local capability injection, focused-window routing, and resource handoff.

Neither adapter owns mail state semantics. When both expose the same operation, they call the same handle method or a shared projection/mutation helper below the handle.

### 5.22 Shutdown and task ownership

Long-lived runtime tasks are owned by the handle or by services reachable from it. The shutdown handle stops account runtimes, closes view subscriptions, drains/persists queued mutation work, flushes stores, closes provider connections, and waits for runtime tasks that must finish before process exit.

Server and desktop hosts may cancel transport tasks after runtime shutdown begins. They must not abandon provider mutations that the runtime accepted durably.

## 6. UI sessions and views

### 6.1 Session registry

A UI session represents one renderer connection to the runtime. The session registry tracks active views, subscriptions, and transient renderer capabilities.

Bundled mode may have one main UI session plus focused windows. Each window still talks to the same authority runtime.

### 6.2 View registry

The view registry maps `ViewId` values to runtime-owned view state. It stores the canonical descriptor, latest revision, latest snapshot, subscribers, and cleanup policy for each active view.

The registry owns current view windows and pushes updates to subscribers.

### 6.3 View cleanup

When a renderer closes a view or disconnects, the runtime may release active-view state after a grace period. Reopening the view creates or reuses runtime state according to the view policy.

## 7. View operation flow

### 7.1 Opening a query view

Opening a query view follows this shape:

```text
UI openView(mailList descriptor)
 -> runtime canonicalizes QueryScope and window request
 -> query/view service reads SQLite projection
 -> view registry stores current ViewSnapshot
 -> runtime returns or streams view.snapshot
 -> background sync or provider status may later update the view
```

No provider call is required to render the initial local window.

The mail-list snapshot contains stable row IDs, row projections, ordering metadata needed by the renderer, cursor/window continuation state, row pending markers, and list-level loading/error affordances. The UI may preserve scroll anchor and selection, but it does not compute row membership or replacement rows.

### 7.2 Applying state assertions

When sync, provider reconciliation, or local mutation changes state:

```text
state assertion appended
 -> event bus broadcasts assertion
 -> view registry determines affected active views
 -> query/view service recomputes affected windows
 -> runtime streams replacement state to subscribers
```

The runtime may use dependency analysis to skip recomputing views that cannot be affected. This is an optimization; correctness comes from backend query evaluation.

Affected subscriptions receive `view.replace` with a new `ViewRevision`. If the runtime cannot cheaply determine whether a view was affected, it recomputes or marks the view updating and then sends a replacement snapshot.

The targeted-update vertical slice for `message.keywords_changed` uses the post-state message assertion emitted by the store. The authority view registry checks open `mailList` views, recomputes affected windows through the query service, and streams `view.replace`; subscribers that resume behind the latest revision receive a fresh `view.snapshot` instead of replaying stale frames.

### 7.3 Conversation and detail views

Conversation and message detail views use the same token model as list views. If a message assertion changes `ConversationRef`, `bodyToken`, or `attachmentToken` for a visible view, the runtime refreshes the affected view state and streams the result.

A detail or conversation view may enter `loading` or `updating` while body, attachment, or envelope data is refreshed. The renderer shows the runtime-supplied affordance and does not compare tokens itself.

## 8. Mutation pipeline and catalog

### 8.1 Named mutation flow

A UI mutation follows this shape:

```text
UI runMutation(name, args, clientMutationId)
 -> runtime validates idempotency and authorization/context
 -> runtime persists idempotency mapping and mutation record
 -> mutation coordinator applies local effect when allowed
 -> state assertion and pending mutation state are emitted
 -> provider command or sync work is queued/executed when required
 -> provider result settles, confirms, or rejects the pending mutation
 -> runtime emits settlement state
```

Accepted mutations are durable runtime state. The runtime records the client id, runtime mutation id, name, args hash, submitter session, affected resources, local before/after state when needed for undo/settlement, provider work state, and terminal outcome.

### 8.2 Mutation argument rules

Mutation args carry explicit account/source context and resource identifiers. A message mutation may target one or more messages, but every target is account-scoped.

Mutation args express user intent, not transport commands. For example, archive and trash may target roles; the runtime resolves the current account mailbox for that role. The renderer should not be required to look up role mailboxes before submitting ordinary actions.

A repeated `clientMutationId` with the same mutation name and args returns the existing runtime mutation record or terminal result. The same id with different args is rejected as `invalid_mutation`.

### 8.3 Local effect policy

A local effect is a durable authority-runtime state change that can update views before provider reconciliation finishes. Local effect does not mean provider success.

Local effects emit normal state assertions and pending markers. Provider confirmation clears pending markers or advances settlement. Provider rejection, conflict, or timeout settles through the same mutation record.

### 8.4 Message keyword mutations

| Mutation | Args | Local effect | Provider work | Failure/settlement |
| --- | --- | --- | --- | --- |
| `message.setReadState` | targets, `read: boolean` | Add or remove the provider seen keyword in local message state. | Set provider keyword state. | Retry transient failures; on permanent rejection refresh affected messages and settle failed or conflict. |
| `message.setFlaggedState` | targets, `flagged: boolean` | Add or remove the provider flagged keyword in local message state. | Set provider keyword state. | Retry transient failures; on permanent rejection refresh affected messages and settle failed or conflict. |
| `message.setUserTags` | targets, normalized user tag list or add/remove delta | Update non-system user keywords in local message state. | Set provider labels/keywords according to provider policy. | Invalid tags reject before local effect; provider mismatch settles failed or conflict with runtime options. |

The runtime owns keyword normalization for system keywords and user tags. Renderer-side validation and completion are allowed, but the runtime is the authority for accepted keywords.

### 8.5 Message mailbox mutations

| Mutation | Args | Local effect | Provider work | Failure/settlement |
| --- | --- | --- | --- | --- |
| `message.moveToMailbox` | targets, mailbox id | Replace or update mailbox membership according to the account mailbox model. | Apply provider mailbox/label move. | Missing/inaccessible mailbox rejects before local effect; provider rejection refreshes affected messages and settles failed or conflict. |
| `message.moveToRole` | targets, role: `inbox`, `archive`, `trash`, or `junk` | Resolve role mailbox and update local membership. | Apply provider move. | Missing role mailbox rejects before local effect. |
| `message.archive` | targets | Alias of `message.moveToRole(role=archive)`. | Apply provider archive/move. | Same as role move. |
| `message.trash` | targets | Alias of `message.moveToRole(role=trash)`. | Apply provider trash/move. | Same as role move. |
| `message.restoreToInbox` | targets | Alias of `message.moveToRole(role=inbox)`. | Apply provider move. | Same as role move. |
| `message.destroy` | targets | Mark pending destruction and remove from active ordinary list windows. | Permanently delete through provider when supported. | Not invertible by default; provider rejection restores or refreshes affected runtime state and settles failed. |

Mailbox mutations store enough before-image state for runtime-backed undo when the mutation is invertible.

### 8.6 Draft and compose mutations

| Mutation | Args | Local effect | Provider work | Failure/settlement |
| --- | --- | --- | --- | --- |
| `draft.save` | draft id or compose intent, headers, recipients, body, attachments | Persist draft state locally, update body/attachment tokens, and update draft views. | Save or update provider draft when supported; otherwise queue provider sync work. | Local validation failures reject before effect. Provider failures leave the local draft durable with queued/failed settlement state. |
| `draft.discard` | draft id | Mark draft discarded locally and remove from compose/draft views. | Delete provider draft when one exists. | Provider failure leaves reconciliation work queued or settles failed while preserving recoverability. |
| `message.send` | draft id or complete send request, optional expected draft revision | Persist pending send/outbox state. Does not assert delivered/sent state until provider confirms. | Submit through provider send path and then reconcile sent/draft state. | Duplicate prevention relies on durable idempotency. Provider rejection keeps or restores editable draft state with failed settlement. Conflict means the draft changed or identity/provider state requires user choice. |

`message.send` is the strictest idempotency case. The runtime must persist the accepted mutation record before provider submission. Retrying the same `clientMutationId` must not send a second message.

### 8.7 Settings and account mutations

| Mutation | Args | Local effect | Provider work | Failure/settlement |
| --- | --- | --- | --- | --- |
| `settings.patch` | sparse application settings patch | Persist local settings and update settings views. | None unless the setting schedules runtime work. | Invalid patch rejects before effect; runtime work failures become status or settlement state. |
| `account.create` | account config and secret instruction | Persist config/secret, create account runtime status, update account/settings views. | Start or verify provider runtime according to args/policy. | Secret/config failures reject before effect; provider failures become account status when possible. |
| `account.patch` | account id, sparse config/secret patch | Persist config/secret changes and converge account runtime. | Restart/reconnect/verify when affected fields require it. | Failed provider reconnect becomes account status; invalid config rejects before effect. |
| `account.enable` / `account.disable` | account id | Toggle enabled state and update runtime status. | Start or stop provider runtime. | Stop/start failures settle through runtime status. |
| `account.delete` | account id, retention choice when supported | Remove account config, stop runtime, update views, and apply configured local-data retention. | Provider work only when the mutation contract explicitly requires it. | Local delete must leave recoverable cleanup status if background cleanup fails. |
| `sync.trigger` | account id, mode | Record sync request/status. | Account runtime performs sync. | Trigger rejection or sync failure is runtime status, not renderer-owned retry logic. |

Settings/account mutations may be local-only, but they still use named mutation records when invoked through the renderer adapter so settlement and multi-window updates are consistent.

### 8.8 Runtime support mutations

| Mutation | Purpose |
| --- | --- |
| `mutation.retry` | Retry a failed or queued runtime mutation when the mutation contract allows retry. |
| `mutation.undo` | Apply a runtime-produced inverse for an invertible confirmed or locally applied mutation. |
| `mutation.resolveConflict` | Submit a selected runtime-provided conflict option for a mutation in conflict state. |

Undo is runtime-backed. The renderer may expose undo UI, but the runtime stores the before-image or inverse needed to perform it.

### 8.9 Settlement states

The mutation catalog uses the settlement states defined in the adapter interface: `accepted`, `localApplied`, `queued`, `confirmed`, `failed`, and `conflict`.

A mutation that has no provider work may move from `accepted` to `localApplied` to `confirmed` in one runtime turn. A mutation with provider work may stay `queued` while offline or retrying.

### 8.10 Reconciliation failures

If provider reconciliation fails, the runtime either retries, emits recoverable failed state, refreshes affected objects from provider/store truth, or exposes conflict options according to the mutation contract.

The UI renders runtime settlement state and may offer user actions, but it does not own conflict resolution.

## 9. Event and state streams

### 9.1 Runtime event bus

The event bus is the internal publication channel for state assertions, coarse lifecycle events, account status, sync progress, and mutation settlement.

The `/v1/events` API and UI runtime adapter may both consume this bus through different transports.

### 9.2 Sequence handling

State assertions appended to durable event history carry backend sequence numbers. UI sessions may use sequence numbers for adapter reconnects or focused-window handoff, but bundled application correctness should not require a network-style reconnect protocol for ordinary in-process updates.

## 10. Security and storage

### 10.1 Runtime-owned roots

Bundled mode resolves runtime-owned roots before building the authority runtime handle:

| Root | Contents |
| --- | --- |
| Config root | Non-secret app settings, account settings, smart-mailbox definitions, automation rules, secret references, and account assets such as uploaded logos. |
| State root | SQLite store, event history when stored outside SQLite, sync cursors, mutation idempotency records, provider work queues, runtime status snapshots, and daemon/bridge metadata only when a separate daemon mode explicitly owns it. |
| Cache root | Body/blob cache data, attachment cache data, source/raw-message cache data when enabled, and cache metadata. |

The cache root may be a subdirectory of the state root in an implementation. It is still runtime-owned and must not be confused with renderer storage.

Development and test builds may override roots through explicit process configuration. Production bundled mode should use platform application data/config/cache locations. Overrides must not make renderer-owned directories the authority runtime roots.

### 10.2 Renderer-owned storage

Renderer-owned storage is limited to presentation and connection-profile state:

- theme and appearance preferences owned by the renderer
- window geometry and pane sizes
- selected layout, sort UI, and recently focused surfaces
- connection-profile metadata with no secrets
- transient adapter/session state

Renderer-owned storage must not contain SQLite copies, message bodies, attachment bytes, event history, mutation idempotency records, provider credentials, refresh tokens, access tokens, long-lived API tokens, or runtime secret references that can be used without the runtime.

### 10.3 Secret stores

Provider credentials, refresh tokens, and provider access tokens stay in the authority runtime secret store. Config may contain secret references and redacted status only.

If a desktop client profile needs a remote API token for a non-bundled deployment mode, that token lives in a client secret store distinct from the authority runtime provider-secret store. Connection-profile JSON may reference the token but must not inline it.

Secrets must not be written to packaged JavaScript, localStorage, renderer-owned JSON files, logs, crash reports, URLs, query strings, or static frontend assets.

### 10.4 Loopback bridge security

A loopback bridge in bundled mode is a local capability channel, not the authority boundary.

When present, it must:

1. bind only to loopback or an equivalent local-only transport
2. use an unguessable process-local token or capability
3. require the token in an authorization header or equivalent non-URL channel
4. reject tokens in query parameters
5. validate `Host` before route exemptions
6. validate browser origin or referer when present
7. restrict CORS to the packaged app origin and configured development origins
8. keep bridge tokens in memory for bundled mode
9. avoid persisting a port/token file unless running an explicit daemon deployment
10. avoid serving provider secrets or secret-store values to JavaScript

The loopback bridge may expose API tokens to the renderer only as narrow local capabilities. It must never expose provider credentials.

### 10.5 Tauri command surface

The desktop host exposes only named Tauri commands required by the packaged renderer. It must not expose generic filesystem, shell, process, network, or environment access to renderer code.

Every command validates structured input with deny-unknown-field semantics or equivalent validation. Surface descriptors, resource descriptors, profile identifiers, and URL parameters are treated as untrusted renderer input.

Commands that return files, bytes, resource handles, or local URLs return scoped runtime resources, not arbitrary filesystem paths.

### 10.6 Navigation and external URLs

Production bundled mode loads renderer assets from the application bundle. Development mode may load from a local development server, but renderer origin differences must not weaken mail authority boundaries.

The desktop host blocks untrusted in-app navigation. External web links open in the system browser and must use an allowed external scheme such as `http` or `https`. File, shell, custom command, and provider credential schemes are not opened from renderer-provided URLs unless a separate security contract allows a specific scheme.

Email body content remains sandboxed and sanitized according to the mail content contract. Link handling from email content follows the same external-navigation rule.

### 10.7 Logging and diagnostics

Runtime, API, and renderer-forwarded logs must not include provider secrets, bearer tokens, capability URLs, full URLs with sensitive query strings, raw Authorization headers, message body content, or attachment bytes.

Diagnostic metadata such as request IDs, operation IDs, session IDs, event names, and correlation IDs uses bounded safe-token formats. User-visible error messages should not leak local filesystem paths, provider credentials, or internal stack traces.

### 10.8 Resource capabilities

Attachment downloads, message source exports, and cached blob reads use runtime resource operations. A resource operation may return bytes, a Tauri resource handle, or a short-lived local capability URL.

Capability URLs and handles are scoped to the requesting session, expire, and are invalid after logout/session close when possible. They do not encode provider credentials and cannot be broadened by editing path or query components.

### 10.9 Data deletion and retention

Account deletion and cache cleanup are runtime mutations or maintenance tasks. The mutation contract defines whether local message/cache data is removed immediately, queued for cleanup, or retained by explicit user choice.

Renderer storage cleanup must not delete runtime-owned roots directly. It requests runtime cleanup through named mutations or maintenance actions.

## 11. Validation

### 11.1 Bundle startup tests

Tests or smoke checks cover that the bundled app can start without a separately running backend and can open the main renderer after the embedded authority runtime is ready.

### 11.2 Runtime boundary tests

Tests cover that the UI adapter can open a query view, receive initial state, run a mutation, and receive updated view state without provider round trips on the local phase.

### 11.3 Runtime contract and handle extraction tests

Tests cover that the shared runtime contract compiles without Axum, Tauri, or React types; that the authority runtime handle can be built without binding an HTTP listener; and that Axum and Tauri adapters use the same runtime contract for overlapping behavior.

### 11.4 View window tests

Tests cover that mail-list snapshots include stable row keys, opaque continuation cursors, lifecycle affordances, pending row markers, and anchor status for around-anchor window requests.

### 11.5 Multi-window tests

Tests cover two renderer sessions observing the same runtime state. A mutation from one session updates the other through the runtime event bus.

### 11.6 Provider-latency tests

Tests cover provider command delay/failure while local view state updates immediately according to the mutation contract.

### 11.7 Mutation catalog tests

Tests cover read/flag/tag, role move, destroy, draft save, send, settings/account, retry, undo, and conflict-resolution mutations at the runtime boundary. Send tests cover crash/retry idempotency before provider submission so duplicate sends cannot occur from a reused `clientMutationId`.

### 11.8 Storage and secret tests

Tests cover that provider secrets are not persisted in renderer-owned files, connection-profile JSON, localStorage, logs, URLs, or packaged JavaScript. Tests also cover that client remote-profile tokens, when supported, are stored in the client secret store rather than the profile JSON.

### 11.9 Bridge and desktop security tests

Tests cover that loopback bridge tokens are header/capability-only, host validation runs before route exemptions, origins are restricted, query-token auth is rejected, and daemon-style port/token files are not written in bundled mode.

Tests cover that Tauri command input rejects unknown fields or invalid descriptors, external URL opening accepts only allowed schemes, in-app navigation to untrusted origins is blocked, and generic filesystem/shell capabilities are not exposed to renderer windows.
