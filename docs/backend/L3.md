# API runtime-wrapper implementation decisions

## 1. Migration shape

The `/v1` adapter migrates by branch-by-abstraction. `posthaste-server::AppState` now carries the target `AuthorityRuntimeHandle` plus HTTP-adapter-owned state, without exposing legacy service/store/supervisor fields to route handlers.

This preserves current endpoint behavior while keeping mail behavior behind runtime methods and temporary authority-runtime bridge internals.

## 2. Startup assembly

`start_server` still owns HTTP process concerns: dotenv loading, daemon settings, logging, CORS, tracing, auth material, router assembly, Swagger UI, static asset serving, and listener binding.

Config/store/service/secret/event assembly moves to `posthaste-authority-runtime::build_authority_runtime`. `posthaste-server` reads daemon settings from TOML first because those settings are process/HTTP concerns needed before listener setup.

The current server cache root is `state_root/cache`. This follows the runtime L2 allowance that cache roots may be subdirectories of the state root, and keeps root resolution stable until a platform cache-root resolver is specified.

## 3. Temporary API bridge

`AuthorityRuntimeBuild` exposes `api_bridge` with existing `MailService`, `MailStore`, `SecretStore`, and event sender handles. This bridge is temporary and exists only for compatibility harnesses and migration constructors, not for `AppState` route fields or authority-runtime core method implementations.

`AccountSupervisor` lives in `posthaste-authority-runtime`; `posthaste-server::supervisor` is a compatibility re-export for tests and remaining adapter imports.

## 4. Runtime read service

The first migrated API read family is backed by an authority-runtime `AccountReadService`, not by ad hoc API helper logic.

Concrete choices:

- `RuntimeCore::get_app_settings(RuntimeCaller) -> AppSettings` backs `GET /v1/settings`.
- `RuntimeCore::list_accounts`, `get_account`, and `resolve_account_scope` centralize account overview construction and enabled-account scope.
- `RuntimeCore::list_mailboxes`, `list_smart_mailboxes`, `get_smart_mailbox`, and `list_tags` use explicit `AccountScopeRequest` inputs instead of letting API handlers derive default scope from response payloads.
- `posthaste-authority-runtime` implements these reads through `AccountReadService`, which currently wraps the existing `MailService` while preserving one runtime-owned account-scope path.
- The HTTP handler maps `RuntimeError` into the normal `/v1` `ApiError` envelope.

`AccountScopeRequest::EnabledAccounts` is the runtime-owned way to request the default enabled-account scope. API adapters must not implement this by listing accounts and manually filtering a response payload.

## 5. Supervisor ownership migration

Provider-backed routes cross a live account-runtime boundary. The migration is now split along the runtime crate boundary:

1. API handlers call `AuthorityRuntimeHandle` for provider-backed reads and sync commands.
2. `posthaste-authority-runtime` owns the runtime contract methods and the concrete `AccountSupervisor` implementation.
3. `posthaste-server::supervisor` is only a compatibility re-export for tests and remaining adapter code.
4. `LiveAccountRuntimeProvider` remains as an internal runtime seam between handle methods and live account runtime resources.

This keeps Axum handlers out of gateway lookup and makes the account runtime graph transport-free: it can be reused by embedded desktop/runtime adapters without moving HTTP routing code.

## 6. Migrated read routes

The current runtime-backed reads are:

- `GET /v1/settings`
- `GET /v1/accounts`
- `GET /v1/accounts/{account_id}`
- `POST /v1/read` operations: `Account/list`, `Mailbox/list`, `SmartMailbox/list`, and `Tag/list`
- `GET /v1/sources/{source_id}/mailboxes`
- `GET /v1/smart-mailboxes`
- `GET /v1/smart-mailboxes/{smart_mailbox_id}`
- `GET /v1/sender-addresses`
- `GET /v1/sources/{source_id}/identity`
- `GET /v1/sources/{source_id}/messages/{message_id}/reply-context`
- `POST /v1/sources/{source_id}/commands/sync`
- `POST /v1/sources/{source_id}/commands/send`
- message command routes for set-keywords, add-to-mailbox, remove-from-mailbox, replace-mailboxes, and destroy
- provider-backed message detail and attachment fetches
- source, global search, smart-mailbox, and conversation listing routes
- search/cache visibility side-effect recording for message-search result pages
- `PATCH /v1/sources/{source_id}/mailboxes/{mailbox_id}`
- `GET /v1/events`

These routes still use the temporary runtime bridge inside authority runtime for some service/store access, but the API adapter path now goes through `AuthorityRuntimeHandle`. Provider gateway, event publication for migrated message commands/details, sync ownership, query parsing/evaluation, saved-query expansion, search/cache visibility bookkeeping, and event backlog/live subscription ownership live in `posthaste-authority-runtime`.

Mail-list routes use `RuntimeCore::query_mail_page` instead of route-shaped runtime methods. HTTP aliases translate route parameters into query text: `in:Inbox` selects a saved smart mailbox, `in:Account/` selects a concrete source, `in:Account/Archive` selects a concrete mailbox under that source, and `conversation:<id>` selects messages in a derived conversation. Conversation-grouped lists use the `CollapsedByConversation` presentation; conversations remain derived message groupings, not independently mutable runtime objects.

For `GET /v1/events`, the API adapter builds `EventFilter`, calls `RuntimeCore::subscribe_events`, chains the returned replay and live domain events, and maps each event to the established SSE frame shape. The server no longer queries `MailService::list_events` or subscribes to the broadcast channel directly for this route.

## 7. Migrated account mutations

Account CRUD/lifecycle/config mutations that manage mail authority state now enter through `AuthorityRuntimeHandle` methods:

- `POST /v1/accounts`
- `PATCH /v1/accounts/{account_id}`
- `POST /v1/accounts/{account_id}/verify`
- `POST /v1/accounts/{account_id}/enable`
- `POST /v1/accounts/{account_id}/disable`
- account logo metadata updates from `POST /v1/accounts/{account_id}/logo`
- `DELETE /v1/accounts/{account_id}`
- `POST /v1/config:reload`
- `GET /v1/oauth/callback` after the adapter completes provider code exchange

The runtime contract carries adapter-neutral mutation payloads for these routes where the payload is transport-neutral. OAuth callback materialization uses authority-runtime handle methods because token-exchange types currently live with the authority OAuth client. The Axum adapter keeps HTTP request/response schemas and maps stable API errors from runtime error codes, while `posthaste-authority-runtime` owns service writes, secret writes, event append/broadcast, token-set secret writes, and supervisor start/stop/verify/reload calls.

Settings and smart-mailbox config mutations now also enter through `AuthorityRuntimeHandle` methods:

- `PATCH /v1/settings`
- `POST /v1/automation-rules:preview`
- `POST /v1/smart-mailboxes`
- `PATCH /v1/smart-mailboxes/{smart_mailbox_id}`
- `DELETE /v1/smart-mailboxes/{smart_mailbox_id}`
- `POST /v1/smart-mailboxes:reset-defaults`

Authority runtime owns settings normalization, config writes, automation backfill enqueue checks, smart-mailbox config writes, and config event append/broadcast for these routes. Semantic config validation for account settings, default-account references, and automation rules comes from `posthaste-domain`, the same source used when the TOML repository loads hand-edited config. The HTTP adapter keeps request extraction, response JSON shape, and preview limit validation.

These routes still use the temporary migration bridge internally for the current service/store/secret/event graph, but the HTTP handlers no longer call those fields or the supervisor directly for migrated account/settings/smart-mailbox mutation behavior. Account logo upload/download byte and static-file cleanup remain in the server because those are HTTP-managed asset concerns; the account appearance metadata and account delete resource linkage are runtime-owned. OAuth start routes still use HTTP-owned pending browser flow state and provider authorization URL shaping.

## 8. Test harness strategy

Most existing integration harnesses still seed stores and construct `AppState` directly. They use `AppState::runtime_handle_for_migration` or the account-runtime-provider variant to attach a runtime handle to the seeded service/store/event graph.

Harness-owned service/store/supervisor/event handles remain on harness structs for fixture setup and assertions. They are not exposed through `AppState`, keeping route state focused on the runtime handle and HTTP concerns.

## 9. Architecture guard

`crates/posthaste-server/tests/runtime_wrapper.rs` includes a route-module guard against new direct construction of `MailService`, `DatabaseStore`, or `AccountSupervisor` under `src/api` outside test modules.

The guard is intentionally simple. It is a fitness function for the wrapper migration, not a general Rust dependency analyzer.

## 10. Assertions

| ID | Sev. | Assertion |
| --- | --- | --- |
| appstate-runtime-http-only | MUST | `AppState` carries `AuthorityRuntimeHandle` plus HTTP-adapter-owned state, not legacy service/store/supervisor fields. |
| startup-delegates-runtime-assembly | MUST | `start_server` delegates config, store, service, secret store, and event channel assembly to `posthaste-authority-runtime`. |
| server-keeps-http-process-concerns | MUST | Server startup keeps HTTP process concerns such as daemon settings, auth material, CORS, tracing, static serving, docs, and listener binding. |
| api-bridge-temporary | MUST | `AuthorityRuntimeBuild::api_bridge` is temporary and exists only for compatibility harnesses and migration constructors, not runtime-core method dependencies. |
| supervisor-runtime-owned | MUST | `AccountSupervisor` is owned by `posthaste-authority-runtime`; server imports are compatibility re-exports only. |
| harness-attaches-runtime | MUST | API integration harnesses that construct `AppState` directly attach a runtime handle through the migration helper and keep fixture handles outside route state. |
| first-api-read-runtime-backed | MUST | `GET /v1/settings` reads through `AuthorityRuntimeHandle`, not directly through `AppState.service`. |
| account-read-service-owns-scope | MUST | Enabled-account default scope is resolved by authority runtime read service through `AccountScopeRequest`, not by API handlers filtering account-list response payloads. |
| account-list-runtime-backed | MUST | Account list/get and `/v1/read Account/list` use runtime account read methods. |
| typed-read-catalog-runtime-backed | MUST | `/v1/read` mailbox, smart-mailbox, and tag list operations use runtime read methods. |
| collection-list-routes-runtime-backed | MUST | Mailbox and smart-mailbox list/get routes use runtime read methods where those methods exist. |
| supervisor-ownership-migration | MUST | Concrete account supervisor/gateway ownership lives in `posthaste-authority-runtime`; server exposes only adapter state and compatibility re-exports. |
| provider-backed-compose-reads-runtime-backed | MUST | Sender-address, identity, and reply-context read routes use runtime methods rather than direct store/service/gateway calls. |
| sync-command-runtime-backed | MUST | Manual account sync commands call runtime methods and provider seams rather than the supervisor directly. |
| account-mutations-runtime-backed | MUST | Account CRUD/lifecycle/verify/reload-config routes call runtime mutation methods, with authority runtime owning service writes, secret writes, events, and supervisor lifecycle calls. |

| runtime-error-api-mapping | MUST | Runtime errors crossing `/v1` are mapped into the stable API error envelope. |
| no-new-route-service-graphs-guard | MUST | A test guard rejects new service/store/supervisor graph construction in route modules. |
