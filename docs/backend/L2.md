## 1. Crate structure

### 1.1 Backend crate roles

The backend is split by contract boundary:

| Crate | Role |
| --- | --- |
| `posthaste-domain` | Domain model, service boundary, provider/store/config/secret ports, provider policy, sync batch types, domain events. |
| `posthaste-config` | TOML-backed configuration repository and atomic config writes. |
| `posthaste-store` | SQLite-backed authority store, read projections, sync application, command persistence, event history, cache state. |
| `posthaste-engine` | JMAP gateway, JMAP sync, JMAP push transports, JMAP compose helpers, mock gateway support. |
| `posthaste-imap` | IMAP/SMTP gateway, IMAP discovery, sync, mutation, lazy body/blob fetch, SMTP submission. |
| `posthaste-runtime-contract` | Transport-neutral runtime contract: caller context, sessions, views, frames, coverage, named mutations, resources, settlement, and errors. |
| `posthaste-authority-runtime` | Authority runtime implementation over config, secrets, SQLite store, domain service, provider gateways, account supervisor, event bus, views, mutations, cache, and resources. |
| `posthaste-server` | Axum `/v1` API adapter, auth/authz, OAuth HTTP routes, OpenAPI/AsyncAPI serving, CORS, tracing, optional static app serving, and daemon/loopback process concerns. |
| `posthaste-observability` | Logging and tracing helpers shared by backend crates. |
| `posthaste-lab` | Verification and lab tooling outside the primary mail runtime, including `config validate` for checking a TOML config directory before use. |

### 1.2 Dependency direction

`posthaste-domain` defines backend domain contracts. `posthaste-runtime-contract` defines the UI/API-facing runtime contract. Store, config, and provider crates implement domain contracts. The authority runtime crate assembles those implementations behind the runtime contract. The server crate adapts the runtime contract to HTTP.

```text
posthaste-server
  -> posthaste-runtime-contract
  -> posthaste-authority-runtime
  -> posthaste-observability

posthaste-authority-runtime
  -> posthaste-runtime-contract
  -> posthaste-domain
  -> posthaste-config
  -> posthaste-store
  -> posthaste-engine
  -> posthaste-imap
  -> posthaste-observability

posthaste-config -> posthaste-domain
posthaste-store  -> posthaste-domain
posthaste-engine -> posthaste-domain
posthaste-imap   -> posthaste-domain
```

Provider crates should not depend on API handler types. Store code should not depend on provider crate types. API handlers should not become the place where provider/store normalization happens.

#### 1.2.1 Motivation

The domain crate is the common language. Keeping it below provider, store, config, and server code lets backend pieces vary independently while preserving one set of mail concepts.

## 2. Runtime assembly

### 2.1 Authority runtime handle

The authority runtime crate assembles one authority runtime handle before any transport adapter is built. The handle is the process-local implementation of the shared runtime contract for mail behavior.

The handle contains or references:

1. configuration repository
2. local store
3. secret store
4. domain service
5. account supervisor
6. event log and event broadcast channel
7. query/view service and view registry
8. mutation coordinator and idempotency store
9. body/blob cache service
10. resource resolver
11. account/setup and OAuth flow state when enabled

API handlers, desktop runtime adapters, tests, and maintenance tasks use this handle through the runtime contract rather than constructing separate mail behavior.

### 2.2 Handle construction

Handle construction is transport-free:

```text
AuthorityRuntimeBuildConfig { roots, process settings, adapter capabilities }
 -> open config repository
 -> initialize/import defaults when needed
 -> open secret store
 -> open SQLite store and migrations
 -> build domain service
 -> sync source projections
 -> create event bus
 -> create account supervisor
 -> create query/view service
 -> create mutation coordinator
 -> create resource resolver
 -> return AuthorityRuntimeHandle and ShutdownHandle
```

The handle builder may return process support values, such as log guards or API auth material, but those values are not part of mail behavior.

### 2.3 Handle method groups

The authority runtime handle exposes method groups, not transport routes:

| Group | Examples |
| --- | --- |
| Lifecycle | start enabled accounts, reload config, report runtime/account status, graceful shutdown. |
| Reads | settings/accounts/mailboxes/smart mailboxes/tags, message detail, conversation view, local query pages. |
| Views | connect renderer session, open/update/close views, subscribe to view frames. |
| Mutations | run named mutation, retry, undo, resolve conflict, inspect mutation state. |
| Events | subscribe to runtime events, read event history for API catch-up/snapshot. |
| Resources | resolve attachment/body/source resources into bytes, handles, or scoped local capabilities. |
| API compatibility | build shared API projections and command responses for `/v1` adapters. |

Methods accept domain/runtime inputs plus an adapter-neutral caller context. They do not accept Axum extractors, HTTP headers, Tauri window handles, or React/UI types.

### 2.4 Server and API adapter assembly

The Axum API router is an adapter over the authority runtime handle. It owns HTTP extraction, authorization, error serialization, and OpenAPI/AsyncAPI serving. It does not own a second service/store/supervisor graph.

Server startup follows this shape:

```text
load process settings
 -> build authority runtime handle from posthaste-authority-runtime
 -> build API adapter state around RuntimeCore/AuthorityRuntimeHandle
 -> build API router over adapter state
 -> start account runtimes for enabled accounts
 -> listen for API requests and event subscribers
```

API adapter state may contain HTTP-only concerns such as auth middleware configuration, OpenAPI/AsyncAPI artifacts, CORS settings, account-logo static roots, and OAuth redirect helpers. Mail reads, mutations, view state, provider access, and event history still flow through the runtime handle.

The compatibility API exposes `POST /v1/views` and `GET /v1/views/{view_id}/stream` as HTTP/SSE adapters over `RuntimeCore::open_view` and `RuntimeCore::subscribe_view`. The routes may serialize runtime view frames, but they must not recompute query windows outside the authority runtime.

### 2.5 Bundled application embedding

The desktop host embeds the same authority runtime handle. It may add Tauri startup, window management, local capability injection, renderer IPC, or a temporary loopback bridge, but it must not fork backend mail contracts.

Bundled application startup follows the runtime deployment sequence:

```text
resolve platform paths
 -> build authority runtime handle
 -> start account runtimes for enabled accounts
 -> register renderer runtime adapter over handle
 -> open renderer windows
```

The Tauri adapter uses the handle's session, view, mutation, resource, and event methods. It does not call Axum handlers to implement primary renderer mail behavior, except while a contained loopback bridge is intentionally used during migration.

### 2.6 Startup failure policy

Startup should fail early when a required local dependency cannot be opened. Account-specific provider failures should usually become account runtime status, not whole-server startup failure.

### 2.7 Shutdown policy

The handle exposes a graceful shutdown path. Shutdown stops renderer sessions, closes view subscriptions, asks account runtimes to stop, drains or persists queued mutation/provider work, flushes stores, and releases provider connections. Adapters call shutdown; they do not tear down account runtimes directly.

## 3. Service structure

### 3.1 Service inputs

The domain service receives:

- a config repository for account and app configuration
- store traits for reads, writes, sync state, events, commands, source projections, and cache work
- explicit account context for account-scoped operations
- provider gateway references when an operation needs remote access

The service does not create provider connections. It uses a gateway supplied by the account runtime or caller for the duration of the operation.

### 3.2 Service outputs

The service returns domain values, command results, sync results, and domain errors. Transport adapters map those outputs into API responses, logs, tests, or runtime status updates.

When the service creates domain events, the caller is responsible for publishing them through the runtime event channel after the relevant state change is durable or observable.

### 3.3 Service operation groups

Service methods group around backend contracts:

| Group | Shape |
| --- | --- |
| Configuration | Read, update, reload, and diff account/app settings. |
| Reads | Compose local projections from config and store state. |
| Sync | Load cursors, call provider sync through a gateway, apply sync batches, record follow-up work. |
| Lazy content | Fetch body/blob data through a gateway and persist cacheable results. |
| Mutations | Execute provider commands, apply local command results, and create events. |
| Automation/cache work | Use local projections and provider gateways to perform backend maintenance work. |

## 4. Provider structure

### 4.1 Gateway implementations

Provider gateway implementations live outside the server crate:

| Driver | Gateway implementation |
| --- | --- |
| JMAP | `posthaste-engine` live gateway. |
| IMAP/SMTP | `posthaste-imap` live gateway. |
| Mock | development/test gateway implementing the same provider contract. |

The server chooses the gateway implementation from account configuration and provider policy when an account runtime connects.

### 4.2 Provider connection structure

A live provider connection includes the authenticated protocol client, provider profile/policy, account settings needed by the driver, and any transport state needed for sync or push.

Provider drivers may cache discovery results or live capability state for the connection lifetime. Durable sync state belongs in the store, not only in the live connection.

### 4.3 Provider operation flow

Remote operations follow this shape:

```text
runtime or service has account context
 -> runtime resolves or creates provider gateway
 -> service calls gateway operation
 -> gateway speaks provider protocol
 -> gateway returns domain record/result/error
 -> service applies local state changes through store contracts
```

Provider-specific retries, token refresh, and reconnects belong at the runtime/gateway edge. Domain service code should see provider results through the gateway contract.

## 5. Store structure

### 5.1 Local database role

The store contains local mail state, sync state, event history, and projections used by backend reads. It is optimized for local runtime/API reads while preserving enough provider identity and cursor state for correct sync.

The database is backend-private. API responses are projections over store state, not direct table exposure.

### 5.2 Write path

Sync and command writes enter through store write contracts. A write may touch several record families in one transaction:

- mailbox records
- message records
- optional conversation/thread projection indexes
- mailbox/message membership
- keyword state
- message body or attachment metadata
- sync cursors
- source projections
- event records
- cache work queues

### 5.3 Read path

Read methods return projections needed by the service and API handlers:

- accounts and source metadata composed with config
- mailbox and smart mailbox views
- message lists and derived conversation views
- message detail and cached body state
- sender, identity, tag, and command support data
- runtime-visible event history

Read code should preserve account scoping and pagination rules before data leaves the backend.

## 6. Config and secret structure

### 6.1 Config structure

Configuration is loaded into a snapshot. Backend reads use the snapshot, and writes replace the relevant TOML state atomically before updating the in-memory view.

`posthaste-domain` owns the semantic config validators. The TOML repository assembles files into a candidate snapshot, validates the whole snapshot, and only then swaps it into the repository view. Runtime mutation paths use the same domain validators for account settings, default-account selection, and automation settings so API/runtime writes and hand-edited TOML share one source of validation truth.

A reload compares the new validated snapshot with the previous snapshot and reports a diff. If parsing or semantic validation fails, reload rejects the candidate snapshot and leaves the previous snapshot active. Runtime code uses the diff from accepted reloads to decide which account runtimes need lifecycle changes.

Config files contain non-secret settings, account/provider metadata, secret references, and redacted secret status. They do not contain long-lived provider credentials or access tokens.

### 6.2 Root structure

Backend roots are resolved before runtime handle construction. Config, state, and cache roots are runtime-owned. They are not renderer local-storage locations and are not inferred from webview state.

The state root contains the SQLite store, event history when external to SQLite, sync cursors, mutation idempotency records, and provider work queues. The cache root contains body/blob and attachment cache data. The config root contains non-secret settings and account assets.

### 6.3 Secret structure

Secret storage is addressed through secret references stored in configuration. Provider connection code resolves the reference to credentials or tokens before building a gateway.

OAuth refresh or credential rotation updates the secret store. It does not rewrite unrelated account TOML and must not copy refreshed tokens into config, logs, or renderer storage.

### 6.4 Account lifecycle after config changes

Config changes that affect account enablement, provider settings, credential references, or sync behavior flow through the supervisor:

```text
config write or reload
 -> config diff
 -> supervisor compares affected accounts
 -> stop, start, restart, or leave runtime unchanged
 -> publish status or config-related events when needed
```

## 7. Runtime flows

### 7.1 Account runtime loop

Each enabled account has an account runtime. The runtime owns provider connection lifecycle and background work for that account.

A runtime loop handles:

- startup sync
- scheduled polling
- manual sync commands
- provider push or IDLE hints
- cache maintenance
- automation/backfill work
- shutdown requests
- status updates

### 7.2 Sync flow

Sync is coordinated by the account runtime and applied by the service/store:

```text
sync trigger
 -> runtime ensures provider gateway
 -> service loads sync cursors from store
 -> service calls gateway.sync(account, cursors, mode)
 -> gateway returns sync batch
 -> service applies sync batch through store
 -> service records follow-up cache or automation work
 -> service creates domain events
 -> runtime publishes events and updates status
```

Full or forced sync modes may change which cursors are supplied to the gateway. Provider-specific planning remains inside the gateway.

### 7.3 Read flow

Reads do not require provider access unless the requested operation explicitly fetches lazy remote content.

```text
runtime adapter or API handler
 -> service read method
 -> config snapshot and store projections
 -> domain read model
 -> runtime/API projection mapping
```

Local reads should remain available when a provider connection is down, as long as the requested data is already present locally.

### 7.4 Mutation flow

Mutations follow their named mutation contract. Some mutations apply a durable local phase before provider reconciliation. Others validate or call the provider before exposing user-visible state. The contract decides which path is safe.

```text
runtime/API command
 -> adapter or handler authorizes and validates request
 -> mutation idempotency record is persisted when present
 -> supervisor supplies account gateway when provider access is needed
 -> service applies the local mutation phase when allowed
 -> provider command runs or is queued when required
 -> service applies provider outcome or settlement through store
 -> event is recorded and published
 -> runtime/API returns command state
```

If the provider rejects a mutation because state changed remotely, the backend should surface an explicit error, settle the mutation failed, or schedule/perform reconciliation according to the mutation contract.

### 7.5 Lazy body and blob flow

Message metadata is synced before body or blob content. Lazy content follows this shape:

```text
detail or attachment request
 -> service checks local cached content
 -> if missing, runtime supplies gateway
 -> gateway fetches body or blob from provider
 -> service persists cacheable content or metadata
 -> API returns sanitized body or authenticated blob response
```

Sanitization happens before HTML body content crosses the client boundary.

## 8. Event flow

### 8.1 Event creation

Domain events are created by service/store operations that change observable backend state. Runtime status changes may also create observable events.

Message events are built from the same API projection constructors used by HTTP reads. Message mutations produce before/after post-state assertions after the write, including `ConversationRef`, `bodyToken`, and `attachmentToken` when a summary is present. Other client-visible mail state changes produce before/after assertions for their named state. The backend does not emit query-scope invalidation commands. Message changes do not emit separate conversation projection assertions. Coarse lifecycle topics produce explicit topic payloads.

### 8.2 Chokepoint construction

Sync writes and command writes use the same event-construction path for the same object type. A message mailbox change caused by sync and a message mailbox change caused by a command both result in a `message` change assertion with before/after summary state and conversation freshness references.

```text
state change transaction
 -> capture previous summary state when a message exists
 -> apply the state change and recompute affected backend projections
 -> build current summary state when the message still exists
 -> wrap as message assertion, other state assertion, or coarse event
 -> append event to history
 -> publish event to live subscribers
```

### 8.3 Event persistence and publish

Events are appended to backend event history and then published to live subscribers.

```text
state change transaction
 -> event row or event record exists in backend history
 -> runtime/API publisher broadcasts event
 -> clients resume from backend event sequence
```

If a live broadcast is missed, clients recover message state by collapsed catch-up or snapshot through the API event stream. Query pages and conversation envelopes recover through their HTTP read endpoints.

### 8.4 Snapshot construction

Snapshot mode reads the current message projection for one account scope and emits assertion frames using the same constructors as live message events and HTTP reads. Snapshot code must not hand-build a second event shape.

### 8.5 Provider signal separation

Provider push, IMAP IDLE, and polling triggers are runtime inputs. They may cause sync. They do not become client-facing events unless the backend observes a domain change or status change.

## 9. API implementation flow

### 9.1 Router and adapter structure

The server crate builds the API router and attaches shared application state. Runtime adapters and route handlers perform transport work and delegate backend behavior.

An adapter or handler may:

1. authenticate and authorize the request
2. parse path, query, and JSON body input
3. validate API-level constraints
4. call the runtime handle or another backend contract below that handle
5. map domain/runtime results or errors to API responses
6. let the runtime publish message assertions, other state assertions, or coarse events when the operation creates them

### 9.2 Runtime access from handlers

Handlers that need provider access do not create provider connections. They call runtime-handle methods that own account-supervisor/gateway lookup.

Handlers that only read local projections should not require a live provider connection and should use runtime read/query methods when available.

### 9.3 Generated contracts

The server owns API schema generation. Generated OpenAPI and AsyncAPI artifacts are checked against committed files so client type generation can detect drift.

Backend implementation changes that alter external request/response/event shape must update the API contract and generated artifacts.

## 10. Extension points

### 10.1 Adding a provider driver

To add a provider driver:

1. add provider configuration and policy fields
2. implement the provider gateway contract
3. define sync cursor/state needs in the store if existing state is insufficient
4. wire gateway construction into the account runtime
5. add provider parity tests for sync, lazy body, mutations, and send behavior
6. update API/config docs only when client-visible setup or behavior changes

### 10.2 Adding a backend read model

To add a read model:

1. decide whether the data is config-derived, store-derived, or composed
2. add store read projections if needed
3. define the API projection name
4. add service method or extend an existing read group
5. expose through HTTP only after the API contract is specified
6. define event behavior only when the read model needs state assertions or coarse lifecycle events

### 10.3 Adding a mutation

To add a mutation:

1. define the runtime named mutation contract
2. define API command shape only when the mutation is exposed through `/v1`
3. add provider gateway capability or explicit unsupported behavior
4. define local effect, durable idempotency, queued provider work, and settlement state
5. apply local command results through the service/store boundary when the contract allows it
6. define conflict and reconciliation behavior
7. create message assertions, other state assertions, or coarse events after observable state changes
8. test at least one happy path, one idempotent retry path, and one provider rejection/conflict path

### 10.4 Adding an event type

To add an event type:

1. define whether the event is a message assertion, another state assertion, or a coarse lifecycle event
2. for state assertions, define the named API projection used for before/after state
3. ensure the state change is observable through HTTP or snapshot reads
4. append the event after the state change is durable or observable
5. add the event to the event contract and generated artifacts
6. add convergence coverage when clients apply the event as replicated state

## 11. Assertions

| --- | --- | --- |
| domain-is-shared-language | MUST | Backend implementation crates communicate through domain contracts rather than API handler types or provider-specific private types. |
| runtime-contract-crate | MUST | The UI/API-facing runtime contract is available outside `posthaste-server` so server and desktop adapters can share it. |
