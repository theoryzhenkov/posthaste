## 1. Boundary

L4 made the runtime↔backend link a real assertion-replication seam: the backend
streams **base assertions** down, and the runtime (the near node) recomputes its
views from them. The client↔runtime link is the last seam still on the *old*
shape — the runtime **computes the whole view server-side and pushes the entire
`ViewSnapshot`** down on every change. This spec unifies it onto the L4 shape, so
the client becomes a first-class near node fed deltas, the way the runtime
already is.

This is the L5 §9 "deferred unification," now scheduled, and it is **driven by
performance**, not symmetry alone.

## 2. The problem (the cost we are removing)

Two costs, both inherent to the snapshot-push model:

1. **Whole-view push per mutation.** On any change to a served view, the runtime
   runs `ViewRegistry::recompute_view_if_changed` and emits
   `ViewFrame::Replace { snapshot }` carrying the *entire* recomputed view
   (`ViewSnapshot.data` = all rows). Flagging one message re-sends every row in
   the inbox. Cost is O(view), per change, per subscribed client.
2. **Full re-query per event.** That recompute re-runs the mail-list query
   (`reads.query_mail_page`) against the backend on *every* `message.updated`
   event, even though exactly one message changed. Cost is a DB/link round trip
   per event, paid on the runtime regardless of how the result is delivered.

The runtime↔backend link pays neither: the backend sends one `BaseAssertion` for
the changed message; the near node applies it to its held base and re-projects
O(delta). The client↔runtime link should do the same.

## 3. The target shape

The client is a **near node** — it already has the vehicle (the shared replica,
[L2](L2.md)). The unified link:

- **Down-channel carries base assertions, not snapshots.** Incremental change is
  a `BaseAssertion` (the changed message's fold state, the L4 shape), not a
  recomputed `ViewSnapshot`. The whole-snapshot frame survives only for *initial
  load*, *window extension*, and *coverage change* — the cases that genuinely
  replace the base.
- **View computation lives at the near node.** The client's replica
  (`MailListReplica`) folds the served base + its outbox + applied assertions and
  projects rows locally. The runtime stops computing views *for* the client.
- **The runtime recomputes incrementally too.** `ViewRegistry` holds each view's
  served base and applies per-message assertions via the same `MailListReplica`,
  instead of re-querying — removing cost (2) on the runtime independently of the
  client.
- **Coverage replaces sessions; subscribe replaces open_view.** A session becomes
  the client's connection/coverage state; a view becomes a coverage subscription;
  `open_view` becomes `subscribe(coverage)` + read-through for the initial base.
- **One contract.** Stripped of bespoke session/view RPCs, the runtime serves the
  client exactly what the backend serves the runtime, so a single `BackendApi`
  (renamed to a neutral link name) contracts both seams (closing L5 §9).

## 4. Mechanism reuse

Nothing new is invented. The convergence already shared by both seams —
`posthaste-link-core` (`MessageReplica`) and `posthaste-link-replica`
(`MailListReplica`) — does the work at the client exactly as it does at the
runtime. The client WASM replica ([L2](L2.md), behind `VITE_RUNTIME_REPLICA`)
already ingests served rows, folds an outbox, and projects optimistic rows; this
arc **feeds it assertions instead of re-served snapshots and makes it the default
client read path**. The up-channel (`MutationRequest`/`MutationReceipt` + the
`ClientMutationId`↔`RuntimeMutationId` join) is already identical and unchanged.

## 5. Slices

- **U1 — runtime recomputes incrementally (runtime-side perf, no client change).**
  `ViewRegistry` holds each mail-list view's served base and applies per-message
  assertions (read one summary, fold, re-project) instead of re-querying the
  whole page per event. Removes cost (2). The wire to the client is unchanged
  (still a `Replace`, now computed O(delta)). Lowest risk; behavior-preserving
  for clients.
- **U2 — assertion delta on the client down-channel (the main perf win).** Add a
  `RuntimeFrame`/`ViewFrame` variant carrying `BaseAssertion`s (the L4 shape).
  The runtime emits the per-message delta it already computed in U1 instead of a
  whole `Replace`; the client replica applies it. Removes cost (1). Gated on the
  client being a near node (U3).
- **U3 — the replica is the default client read path.** Promote the L2 WASM
  replica from flag-gated to default: finish production wiring + real-browser
  validation, and close the surfaced-failure gap (a keyed `MutationSettlement::Failed`
  + `OperationId`↔`RuntimeMutationId` linkage) so a rejected mutation reverts
  *and* surfaces. The non-replica snapshot path remains a fallback during the
  transition. **This is the load-bearing decision (§6).**
- **U4 — coverage replaces sessions/views.** `open_view` → `subscribe(coverage)`
  + read-through for the initial base; the runtime stops server-side view
  recompute for covered views and serves assertions for the coverage. Sessions
  collapse to connection/coverage state.
- **U5 — one contract.** Fold the client wire onto `BackendApi` (renamed to a
  neutral link name); retire the bespoke `RuntimeFrame` session/view variants
  superseded by assertions + coverage. Closes L5 §9.

## 6. The load-bearing decision

U2's perf win requires the client to *apply* assertions — i.e., to be a near node
(the replica). U3 makes the replica the default client path for all users. The
L2 review found the replica **correctness-safe to dogfood** (rejected mutations
do not stick — a failure re-serves a corrected base), with one open caveat: the
**surfaced-failure gap** (the user briefly sees success; no keyed `Failed` toast).
Closing that needs a runtime lifecycle decision (double-settlement vs
deferred-confirm) + relinking `OperationId`↔`RuntimeMutationId`. U3 must close it
before defaulting the replica on; until then U1 (runtime-side, no client change)
delivers value safely.

## 7. Migration

- Each slice is independently shippable; U1 alone is a behavior-preserving perf
  win behind no flag.
- The whole-snapshot frame is never removed outright: it remains the initial-load
  / window-extend / coverage-change frame, and the non-replica client fallback,
  until U5 retires only the *superseded* variants.
- U2's delta frame is additive (a new frame variant); a client that does not
  understand it falls back to requesting a snapshot, so old and new clients
  coexist during rollout.
- Capability negotiation (does this client apply assertions?) gates whether the
  runtime sends deltas or snapshots to a given subscription.

## 8. Assertions

| ID | Sev. | Assertion |
| --- | --- | --- |
| client-is-a-near-node | MUST | Incremental view change reaches the client as a base assertion the client's replica applies, not as a recomputed whole view. The whole-view frame is reserved for initial load / window extend / coverage change. |
| incremental-recompute | MUST | The runtime recomputes a served mail-list view by applying the changed message's assertion to its held base, not by re-querying the whole page per event. |
| one-replica-both-seams | MUST | The client and the runtime fold the same `link-replica`/`link-core` components; neither reimplements the projection. |
| delta-is-additive | SHOULD | The assertion-delta frame is additive on the wire; a client that does not apply assertions falls back to whole-snapshot frames, so rollout is incremental. |
| one-link-contract | SHOULD | Once coverage replaces sessions/views, a single link contract (`BackendApi`, neutrally named) serves both the client↔runtime and runtime↔backend seams (closes L5 §9). |
