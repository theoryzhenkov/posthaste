## 1. Boundary

### 1.1 What this implements

This L2 implements the **client-layer link node** from [replication L1 §10](L1.md) (the "hosted runtime / multi-device" deployment instance): a device-resident replica that runs on the user's machine, holds an outbox and a cache of authoritative base state, applies the shared local effect to produce optimistic state, and converges with a **remote** runtime by per-mutation confirmation. It runs as a WebAssembly module in the browser; the same node compiles natively for non-browser hosts.

It also implements the factoring that the replica requires: extracting the **single shared predictor** ([replication L1 §4.3](L1.md), `single-local-effect`) — the named-mutation vocabulary and the pure local-effect fold — into a crate that both the authority runtime and the replica depend on, so there is exactly one predictor across deployments.

### 1.2 What this does not implement

- **Partial-coverage replication at scale.** The replica here holds the runtime's *currently served bounded views* (the working set), not the whole account. Interval-set coverage, a background acquisition scheduler, smart-mailboxes-as-atom-expressions, and FTS-as-membership are a later optimization layer (the `client-replica-effort` design); [replication L1 §3.3](L1.md) keeps coverage authority-authored so that layer slots in without renderer or contract change.
- **The bundled-desktop path.** There the runtime is in-process and already instant ([runtime L2](../runtime/L2.md)); the replica is not used. This node exists for the remote-runtime transport.
- **A second predictor.** The replica reuses the extracted predictor unchanged. A hand-written TS or JS reimplementation is prohibited (`single-local-effect`).

### 1.3 Target deployment

The driving deployment is a **hosted runtime**: the runtime runs remotely (cloud), serving one or more devices over the remote API transport ([api L1](../api/L1.md)). Each device runs a replica so the renderer stays instant and offline-capable across the network. The replica is selected by the renderer's runtime adapter ([client L1 §3](../client/L1.md), `runtime-adapter-opaque`); the renderer is unchanged.

## 2. Where the predictor lives

### 2.1 Current state

Today the local effect is the read-time overlay fold in `posthaste-domain` (`service/message_queries.rs`: `apply_operations_to_summary` and the `fold_message_overlay` / `apply_message_overlay` / `mailbox_count_overlay` / `overlay_operations` helpers). It is a pure function over canonical records plus pending operations, but it sits inside `MailService`, coupled to the store, config, and gateway ports. The authority runtime serves folded view state from it ([runtime L2](../runtime/L2.md)).

### 2.2 The shared predictor crate

The pure local effect is extracted into a new crate, `posthaste-link-core`, with no I/O dependencies, that compiles to `wasm32-unknown-unknown`. It contains:

- the **named-mutation vocabulary** (mutation kinds, arguments, stable mutation-id type) shared across links;
- the **local effect** `apply(state, mutation) -> state` over canonical replicated records — message keyword/mailbox/destroy assertions and entity-creating draft/send mutations;
- the **rebase primitive** `replay(confirmed_base, pending_mutations)` and the **settlement-driven retire** rule (§5);
- the **coalescing** rule for successive idempotent assertions on the same entity ([replication L1 §4.4](L1.md)).

`posthaste-domain` depends on `posthaste-link-core` and calls it where the overlay fold lives now (no behavior change); the replica depends on it for its fold. This is the `single-local-effect` invariant made structural: one crate, two callers.

### 2.3 Crate constraints

`posthaste-link-core` must stay WASM-clean: no `tokio`, no `rusqlite`, no native time/filesystem. It operates on owned record types and returns owned results; all I/O (store reads, outbox persistence, transport) is the caller's. The full mutation vocabulary is included from the start (assertions **and** entity creation), per the decision to not phase the predictor.

## 3. The shared predictor crate

### 3.1 Inputs and outputs

The predictor's unit of work is `replay(base, pending) -> projected`, where `base` is a set of canonical records ([state/mail L1 §3](../state/mail/L1.md)) the far node asserted, and `pending` is the ordered outbox of not-yet-confirmed mutations. The result is the optimistic projection the renderer reads. The predictor never performs I/O and never stores its result as truth (`view-is-pure-fold`).

### 3.2 Assertion mutations

Keyword set, mailbox replace, and destroy carry a **desired state** and fold idempotently. Folding the same assertion over a base that already reflects it is a no-op, which is what makes the retire instant unobservable (§5). Coalescing collapses successive assertions on one entity to the latest desired state; a pair that cancels drops to nothing.

### 3.3 Entity-creating mutations

Draft create/update and send hold a **provisional entity** under a near-minted id. The predictor surfaces the provisional entity in the projection; convergence reconciles the provisional id to the authoritative id and dedupes by authoritative id so the provisional and confirmed rows never both show ([replication L1 §5.4](L1.md)). Draft identity is carried as the stable draft key already on the wire (the `X-Posthaste-Draft-Id` mechanism), so a provisional draft and its synced row reconcile by that key.

## 4. The replica node

### 4.1 Components

The replica is a runtime node ([runtime L1 §2.3](../runtime/L1.md)) with these parts:

- **Outbox** — durable, ordered, idempotent on mutation id (`outbox-durable-idempotent`). Holds accepted-but-unconfirmed mutations.
- **Base cache** — the confirmed authoritative records for the working set the replica holds, plus per-view **coverage** (§6).
- **Predictor** — `posthaste-link-core` (§3).
- **Down-channel consumer** — applies ordered assertions and per-mutation settlements (`MutationSettlement`) from the remote runtime.
- **Up-channel sender** — drains the outbox toward the remote runtime as named mutations, preserving mutation ids (`mutation-id-end-to-end`).
- **View server** — recomputes the bounded views the renderer subscribes to (`replay` over base + pending), emitting the same `RuntimeFrame` snapshots/replaces the in-process runtime emits, so the renderer adapter surface is identical.

### 4.2 Relationship to the authority runtime

The replica implements the **same renderer-facing contract** as the bundled runtime ([runtime L2 §5](../runtime/L2.md), `RuntimeCore`: open/close session, open/extend/close view, run mutation, frame stream). The renderer cannot tell which is behind the adapter (`runtime-adapter-opaque`). The remote runtime is the replica's **far node**; the replica forwards mutations to it and consumes its assertions.

### 4.3 What the replica does not do

The replica is not an authority: it runs no provider gateways, no automation rules, no account supervisor. Those stay in the remote runtime. The replica predicts the *local effect* of a mutation and lets the authority's base correct it (`corrections-as-base-updates`).

## 5. Convergence in the replica

### 5.1 The rebase loop

The replica's visible state is `replay(confirmed_base, remaining_pending)` per message ([replication L1 §5.3](L1.md)), realized by `posthaste-link-core`'s `MessageReplica`. Two inputs drive it:

- an **authoritative base update** (a served `ViewSnapshot`/`ViewReplace` whose state is the asserted `after`): the replica replaces the asserted message states in its base and recomputes;
- a **settlement** (`RuntimeFrame::MutationSettlement`): the replica retires the named pending mutation and recomputes.

There is no invalidation graph and no per-action reconciliation; both inputs are applied mechanically and the view is always re-derived.

### 5.2 The confirmation join — settlement, not a scalar watermark

[replication L1 §5.2](L1.md) describes the up/down join abstractly as a confirmation watermark (`lastConfirmedMutationId`, the Replicache model). This runtime **realizes that join per mutation**, not as a single monotonic id: the contract serves `RuntimeFrame::MutationSettlement { mutationId, state }` and lists the still-pending mutations folded into each base as `ViewSnapshot.pendingMutations`. That is strictly more information than a scalar — it tolerates out-of-order and partial confirmation, which a monotonic `lastMutationId` cannot.

The replica therefore retires a pending mutation on its **settlement**, not by advancing a scalar. A mutation is `Confirmed` only after the far node has applied it and served the post-state base (state-before-event, [replication L1 §8.3](L1.md)), so by the time `Confirmed` arrives the base already reflects it and dropping the now-redundant pending op is a visual no-op (`retire-on-confirmation`, no flicker). `pendingMutations` is the far node's authority-authored set of still-folded optimism; the replica uses it for pending UI markers and to reconcile its outbox on snapshot recovery (§6.4).

The client mints a `ClientMutationId`; the runtime assigns a `RuntimeMutationId` and reports the pairing in the `MutationReceipt`. The replica tracks the pairing so a settlement keyed by either id matches the originating outbox entry ([replication L1 §6.2](L1.md), `mutation-id-end-to-end`).

### 5.3 Settlement and failure

`Confirmed` retires the pending mutation. `Failed` retires it and surfaces to the user; the recompute reverts the view to authoritative state (`permanent-failure-surfaces`). Entity-creating mutations additionally reconcile a provisional id to the assigned id on settlement (§3.3). The never-confirms backstop retires an accepted-but-never-confirmed mutation after a bounded number of convergence cycles (`never-confirms-backstop`).

## 6. Working-set coverage

### 6.1 Scope

The replica holds exactly the bases for the views the renderer currently has open — the mail-list window (with its `continuation` cursors), open message details, and open conversations — plus their referenced records. It does not mirror the account.

### 6.2 Coverage is per-view and authority-authored

Each served view snapshot already carries its coverage: the mail-list `continuation` (`before`/`after`, `has_after`) bounds the window; a detail/conversation snapshot covers exactly its object. The replica records this so it can distinguish "absent because unchanged" from "absent because not held" ([replication L1 §3.3](L1.md)) and never reports a window as complete when it holds only a page.

### 6.3 Acquisition

The replica acquires more base only in response to renderer demand: opening a view (snapshot pull for that scope), extending the mail-list window (the existing `extend_session_view` operation), or navigating to a new object. There is no background prefetch in this layer — that is the deferred atoms/scheduler work.

### 6.4 Recovery

A reconnecting replica resumes each open view's down-channel from its cursor; on a gap it recovers that scope by snapshot, then resumes (`snapshot-recovery`). Derived views are recomputed, never resumed.

## 7. Transport and confirmation

### 7.1 Injected transport

The WASM node does not own networking. The JS host injects two capabilities: a **request** function (the up-channel: submit named mutation, open/extend/close view, snapshot pull) and a **stream** function (the down-channel: the assertion/frame SSE stream with resume cursor). These map onto the existing remote API ([api L1](../api/L1.md)) the `httpAdapter` already uses, so the replica reuses the deployed runtime endpoints.

### 7.2 The confirmation signal on the wire

The confirmation join is **already on the wire**, as per-mutation settlement rather than a scalar watermark: `RuntimeFrame::MutationSettlement { mutationId, state }` and `ViewSnapshot.pendingMutations` (the still-folded optimism), with `ClientMutationId`/`RuntimeMutationId` paired in `MutationReceipt` (`crates/posthaste-runtime-contract`). W2 therefore does **not** add a `lastConfirmedMutationId` field; it wires the replica to consume the existing settlement frames and `pendingMutations`, and confirms both reach the client unchanged over the remote transport (they already drive pending markers and failure toasts in the current renderer). The L1 §5.2 "watermark" is the abstract join; this is its realization.

## 8. Renderer adapter surface

### 8.1 The seam

The renderer talks to `getRuntimeAdapter()` ([client L1 §3](../client/L1.md)); implementations today are `httpAdapter` and `fakeAdapter` (`apps/web/src/runtime/`). The replica adds a third, `replicaAdapter`, that satisfies the same `RuntimeAdapter` interface (open/close session, open/extend/close view, run mutation, frame stream). The WASM module exposes these as async functions over `wasm-bindgen`; `replicaAdapter` is a thin JS wrapper that serializes requests in and frames out.

### 8.2 Selection

`replicaAdapter` is selected behind a build flag (`VITE_RUNTIME_REPLICA`), default off, alongside `httpAdapter`. The renderer is unchanged (`runtime-adapter-opaque`); flipping the flag swaps the node behind the adapter. Dogfood runs behind the flag before default-on.

## 9. Persistence

### 9.1 IndexedDB

The replica's durable state — the outbox and the base cache — persists in **IndexedDB** so an accepted mutation and the working-set base survive a reload (the browser analogue of the desktop's `outbox_operation` durability). The outbox store is keyed by mutation id for idempotency; the base cache is keyed by record identity within scope. Derived views are never persisted (recomputed on load).

### 9.2 Rebuildability

Like `mail.sqlite`, the base cache is a rebuildable projection of authority state: on corruption or version skew it is dropped and re-acquired by snapshot. The outbox is **not** rebuildable (it is the only home of unconfirmed intent) and is versioned/migrated, never silently discarded.

## 10. Rollout

Each phase is an independently shippable, conventional commit; native-first where possible so correctness is proven before the WASM boundary.

- **W0 — Predictor extraction.** Create `posthaste-link-core` with the named-mutation vocabulary, the pure local-effect fold (assertions + entity creation), and the rebase + settlement-retire primitive. `posthaste-domain` adopts it with no behavior change. Confirm a `wasm32-unknown-unknown` build of the crate. Suites green.
- **W1 — Replica node (native).** Build the outbox + base cache + rebase loop + down-channel consumer + view server against the `RuntimeCore` contract, driving a mock/real remote runtime. Native tests cover convergence, coalescing, retire-on-settlement, and entity reconcile.
- **W2 — Confirmation on the wire.** Wire the replica to consume the existing `MutationSettlement` frames + `ViewSnapshot.pendingMutations` (and the `ClientMutationId`/`RuntimeMutationId` pairing); confirm they survive the remote transport unchanged. No new scalar field.
- **W3 — WASM packaging.** `wasm-bindgen` the node; expose the adapter surface; inject JS transport (fetch/SSE) and IndexedDB persistence. Bundle-size budget checked.
- **W4 — Web adapter wiring.** `replicaAdapter` behind `VITE_RUNTIME_REPLICA`; renderer unchanged; parity tests against `httpAdapter` behavior.
- **W5 — Hardening + dogfood.** Snapshot recovery, never-confirms backstop, entity convergence (draft/send by id), multi-window, offline. Dogfood behind the flag.

## 11. Open questions

1. **SSE in WASM vs JS-owned stream.** Recommend the JS host owns the EventSource/fetch stream and pushes assertions into the WASM node (one transport implementation, reused from `httpAdapter`), rather than networking inside WASM.
2. **Base cache granularity.** Per-record vs per-view-snapshot storage in IndexedDB; per-record dedupes across overlapping views but needs a small reference/coverage index. Lean per-record with a coverage index.
3. **Worker placement.** Run the WASM node on the main thread or a Web Worker. A Worker keeps the fold off the UI thread but adds a message boundary the adapter must bridge; decide in W3 against measured fold cost.
4. **Multi-window on web.** Bundled desktop shares one runtime across windows; on web each tab is its own replica unless a shared Worker/`SharedWorker` backs them. Start tab-local; revisit if cross-tab coherence is needed.

## 12. Assertions

| ID | Sev. | Assertion |
| --- | --- | --- |
| predictor-single-crate | MUST | The local effect and named-mutation vocabulary live in one crate (`posthaste-link-core`) used by both the authority runtime and the replica; no second predictor implementation exists. |
| predictor-wasm-clean | MUST | `posthaste-link-core` compiles to `wasm32-unknown-unknown` with no I/O, native time, or database dependencies. |
| replica-adapter-parity | MUST | The replica satisfies the same renderer `RuntimeCore`/adapter surface as the bundled runtime; the renderer is unchanged when selected. |
| replica-rebase-only | MUST | The replica applies authority updates by replace-base / retire-on-settlement / recompute; it never patches a derived view or sends cross-layer invalidation. |
| replica-working-set | MUST | The replica holds only the bases for currently open views plus referenced records, with per-view authority-authored coverage; it never mirrors the whole account. |
| replica-outbox-durable | MUST | The outbox persists in IndexedDB, is idempotent on mutation id across reload, and is migrated (never silently discarded); the base cache is rebuildable by snapshot. |
| replica-transport-injected | MUST | The WASM node performs no networking itself; the JS host injects the request and stream transports that map to the remote API. |
| replica-settlement-retire | MUST | The replica retires a pending mutation only on its served `MutationSettlement` (or its drop from a base's `pendingMutations`), not on transport acknowledgement; this realizes the L1 confirmation watermark per mutation. |
| replica-flag-gated | SHOULD | The replica adapter is selected behind a build flag, default off, until dogfood promotes it. |
