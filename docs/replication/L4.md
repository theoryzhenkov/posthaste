## 1. Boundary

This spec makes the **runtime↔backend coherent link** ([replication L1 §2](L1.md)) a real, switchable seam in the implementation. Today the runtime holds the backend in-process (the authority runtime owns `MailService` + the store directly; reads go straight to the store, mutations straight to the service). The link is *designed* but *collapsed*. This turns it into the same shape as the already-shipped client↔runtime link: a **near node** (runtime) talking to a **far node** (backend) through a transport-neutral contract, where the transport is **configurable** — in-process and co-located by default, remote when the two are split across machines.

The mechanism is not new. `posthaste-link-core` (the predictor + `MessageReplica` convergence engine) and the outbox/down-channel/rebase loop were built and proven for the client replica ([replication L2](L2.md)/[L3](L3.md)). This spec applies the **same mechanism to the second seam**, and introduces the transport abstraction both seams share.

### 1.1 What changes and what does not

- **Does not change:** the link semantics, the named-mutation/assertion/watermark vocabulary, the renderer, the API `/v1` surface, or behavior in the default (in-process, co-located) deployment.
- **Changes:** the runtime stops reaching the backend by direct in-process `MailService`/store calls and instead goes through a **`BackendLink`** (the runtime↔backend link contract) carried by a selectable **transport**. The runtime gains a near-node base cache + outbox toward the backend; its served views derive from that cache rather than from direct store reads.

## 2. Current state (the starting point)

- `AuthorityRuntimeHandle.core` holds `service: Arc<MailService>` + `store: Arc<dyn MailStore>` and calls them directly (mutations, detail reads, view recompute, sync).
- The `api-runtime-wrapper` migration (`docs/eph/PLAN-L3-api-runtime-wrapper-migration`) is already retiring *direct service/store access from the API server* in favor of the runtime handle — useful groundwork: it narrows direct backend access to the runtime itself, which is exactly the seam this spec formalizes.
- The backend already publishes domain events (the proto down-channel) and accepts named mutations (the proto up-channel) — they are just consumed in-process.

## 3. The link contract (`BackendLink`)

The runtime↔backend link is **not** the full `MailService` API. It is only the replication channels:

- **Up-channel.** `forward_mutation(named_mutation) -> MutationReceipt`. The runtime forwards a (possibly client-originated) named mutation toward the backend with a stable mutation id; the receipt carries the backend's `RuntimeMutationId` for the confirmation join. Idempotent on the mutation id.
- **Down-channel.** `subscribe(coverage) -> Stream<BaseAssertion>`. Ordered, authoritative before/after state assertions tagged with the confirmation watermark (how far the backend has confirmed the runtime's forwarded mutations). The runtime rebases its base cache on each, retiring confirmed outbox entries; derived views recompute (never invalidate).
- **Coverage.** The backend authors coverage on the base it serves down ([L1 §3.3]) so the runtime can distinguish "absent because unchanged" from "absent because not held." The co-located runtime requests complete coverage; a split runtime may request a working set.

Everything the runtime currently reads from the store (detail, summaries, list pages, counts) becomes **derived state** the near node computes from its base cache — exactly as the client replica derives mail-list rows from its served base. Reads do not cross the link; only assertions (down) and mutations (up) do.

## 4. The transport abstraction (one seam for both links)

There is **one** switchable transport abstraction, shared by both the client↔runtime and runtime↔backend links — not a second mechanism. A `LinkTransport` carries one link's two channels and is selected by configuration.

- **`InProcessTransport`** (default). Direct calls to a co-located far node; zero serialization, instant confirmation. The behavior-preserving default — the co-located deployment must be byte-for-byte the same as today.
- **`RemoteTransport`.** The up-channel is `POST`ed named mutations; the down-channel is an SSE/stream of base-assertion frames + watermark. This is what lets a far node live on another machine.

Transport is chosen **per link from config** (§5), not at build time.

### 4.1 Generalize the existing contract; do not invent a parallel one

The link transport is **not new** — it is the **existing, proven client↔runtime wire** (the `runtime-contract` named-mutation / frame / `MutationReceipt` / watermark vocabulary, carried over HTTP/SSE or in-process) recognized as *the* link transport and **reused** by runtime↔backend. The client↔runtime link is therefore conformant by construction (it is where the contract came from), so there is no client-seam migration churn — the runtime↔backend link adopts the proven shape. One definition, two consumers, no divergence (the same value that drove the lazy-resource unification).

The link contract is the **replication subset** of `runtime-contract` (named mutations up; assertion frames + watermark down) — not the whole `RuntimeCore` surface. W0 factors that subset out as the shared contract.

### 4.2 One Rust implementation, deployed as WASM or native

The client side does **not** reimplement the link in TypeScript — it runs the **same Rust link node**, exactly as the client replica already does ([L2](L2.md), `posthaste-link-wasm`):

- **Browser (web build).** The Rust near node (predictor + convergence + `LinkTransport` framing) compiles to **WASM**. WASM has no socket access, so a thin JS shim performs the raw fetch/SSE I/O and IndexedDB and drives the (sync) WASM node — the existing JS-injected-transport pattern. That shim is a dumb byte pipe, not a reimplementation of the link.
- **Tauri (desktop).** The Rust link node runs **natively** in the Tauri Rust process — full I/O, no WASM — and the webview is a pure view over Tauri IPC. This replaces the current embedded localhost HTTP server: a real but clean simplification.
- **Daemon (headless).** Native Rust, no renderer.

So divergence shrinks to the irreducible: **rendering** (always TS) and, *browser-only*, a dumb I/O shim. The link's *logic* is one Rust codebase everywhere — WASM where it must be, native where it can be. `one-link-transport` holds by sharing the implementation, not merely the contract. The Tauri native-link path is a later slice (it changes the desktop transport from embedded-HTTP to IPC), but it is the end state the contract is designed for.

### 4.3 One replica, two consumers (the read-model twin)

The transport is not the only thing both links share. Each near node also holds a **read-model replica**: the far node's served read data as a confirmed base, the node's own outbox of forwarded-but-unconfirmed mutations folded over it, and the optimistic result served onward. This is what lets **every layer apply optimistic offline updates** — the client when its runtime is unreachable, the runtime when its backend is.

That replica is **one implementation**, shared exactly as the transport is (the same value that drove §4.2). `posthaste-link-replica` (over the `posthaste-link-core` predictor) already is it: its `MailListReplica` takes served rows as `{ message_id, projection }` — the full `MessageSummary` presentation projection — reads the foldable keyword/mailbox state out to seed the predictor, folds the outbox, and writes the result back **preserving every other field**. The browser client runs it as WASM today (`posthaste-link-wasm`). The runtime runs the **same crate natively** as its near node over the runtime↔backend link. One replica, two consumers (native runtime + WASM client), mirroring one transport, two consumers.

For the runtime to derive its served views from that replica rather than from direct store reads, the runtime↔backend **down-channel carries the served read data as the base** — the same row/projection vocabulary the runtime already serves its client (generalized from the client↔runtime wire, per §4.1) — not merely the `MessageFoldState` convergence subset. The foldable subset is what the predictor moves; the projection is what the replica caches and re-serves.

## 5. Configuration and transport switching

Per [L1 §10], deployment chooses placement and transport, not link meaning. The control config (desktop-app owned, per [topology direction]) selects, per link:

- `transport = "in-process"` (default) — co-located; or
- `transport = "remote"` with a base URL — the backend (or runtime) runs elsewhere.

The default for all links is in-process co-located: `client + runtime + backend` in one process, identical to today. Switching a link to `remote` is a config change, not a rebuild. The "advanced: remote runtime URL" knob is the client↔runtime link's `remote` selector; the runtime↔backend selector is its symmetric twin.

## 6. Slicing (mirrors the client-replica W-arc)

- **W0 — factor the shared link contract + transport trait.** *(Landed.)* The transport-neutral link channels (named mutations up; assertion frames + watermark down) are factored out as the `posthaste-link-contract` crate that *both* links speak: `LinkTransport` (§4) is the Rust abstraction over one link's two channels, `BackendLink` the runtime↔backend instantiation, and `DownFrame`/`BaseAssertion`/`LinkCoverage` the wire-shaped down-channel. The up-channel reuses `runtime-contract`'s `MutationRequest`/`MutationReceipt` directly, so the client↔runtime link is conformant by construction; no behavior change (no node is rewired yet — that is W1).
- **W1 — in-process transport.** *(Up-channel landed; down-channel stubbed for W2.)* A `Backend` far node (`posthaste-authority-runtime/src/backend.rs`) is now the single owner of message-command backend access — the runtime's typed command methods and the named-mutation dispatch both funnel through it instead of scattered direct `MailService` calls. `InProcessTransport` (`src/transport.rs`) implements `LinkTransport` over it; the runtime holds a `BackendLink` and the named up-channel (`run_mutation` → `dispatch_named_mutation`) forwards through `BackendLink::forward_mutation` (scope + undo-history stay runtime-side). The co-located deployment is byte-for-byte unchanged (all 27 authority-runtime tests pass through the new path). The down-channel `subscribe` is an empty stream until W2 gives the runtime a base cache to consume it — today views still derive from direct store reads, so an unconsumed down-channel changes nothing.
- **W2 — the down-channel.** *(Landed.)* `InProcessTransport::subscribe` is now real: the backend's authoritative `message.updated` events become **complete** `BaseAssertion`s over their message (the far node reads the message's current summary to author the whole-message state, since a mailbox-move event omits keywords and `MessageReplica`'s base is a whole-message replace), and `deleted` events become removals. A pure `message_event_to_assertion` mapper carries the logic, unit-tested without a store. The near node's outbox + base cache + view-from-cache derivation **fold into W3** (below): in-process the up-channel confirms synchronously, so the base cache merely mirrors the store and the view-read swap is a no-op — they only become load-bearing across the remote split, so building them now would be unwired overhead.
- **W3 — remote transport + the runtime read replica.** *(Config selector + remote client + backend HTTP surface landed; the runtime read replica is W3c.)* `BackendTransportConfig` (`InProcess` default | `Remote { base_url }`) is threaded through `AuthorityRuntimeBuildConfig`; `select_backend_link` builds the `BackendLink` over the config-chosen transport, not at build time (assertion `transport-selected-by-config`). `RemoteTransport` is a real client: the up-channel `POST`s the named mutation, the down-channel opens an SSE stream and parses `data:` frames into `DownFrame`s (a pure `parse_sse_frame` mapper). The wire paths (`LINK_FORWARD_MUTATION_PATH`, `LINK_SUBSCRIBE_PATH`) live in `posthaste-link-contract` so client and far node cannot drift. **W3b landed:** `posthaste-server`'s `link_router(transport)` is the far-node HTTP surface that *serves* those endpoints (POST up + SSE down) over any `LinkTransport` — a split-backend host mounts it over the backend's in-process `BackendLink` (now exposed on `AuthorityRuntimeBuild::backend_link`); the real `RemoteTransport` client and the real `link_router` are proven to meet over loopback HTTP (`backend_link_wire` tests), no mock on either side. **W3c — the runtime read replica (§4.3):** the runtime becomes a native consumer of `posthaste-link-replica` (the same crate the WASM client runs), the down-channel base carries served rows (the projection vocabulary), and `views.rs` derives served snapshots from a `MailListReplica` (and sibling view replicas as needed) instead of direct store reads. In-process with synchronous confirmation the outbox is empty and the replica is a pass-through (behavior-preserving); it lights up under the remote split and optimistic-offline. Sub-slices: **(c1+c2 landed)** the runtime holds a `RuntimeBackendOutbox` (forwarded mutations accepted before the up-channel forward, retired on its receipt) and folds it over every mail-list recompute through the shared `posthaste-link-replica::MailListReplica` (`apply_outbox_overlay`) — served rows are the base, the outbox the pending set, the projection the optimistic result. A no-op short-circuit when the outbox is empty keeps the in-process default byte-for-byte unchanged; a deferred-transport test proves the runtime serves a row optimistically flagged while a forward is in flight, retiring when it completes. Role moves (archive/trash/moveToRole) are not folded optimistically yet (they need account role→mailbox resolution). **(c3 landed — write path)** a real split test (`backend_link_split`): a backend runtime (real store, seeded message) served over `link_router`, and a separate runtime configured `Remote` that forwards a `message.destroy` across HTTP into the backend's authoritative store — production `RemoteTransport` → `link_router` → in-process `Backend`, no mock on either side. It surfaced the read-path dependency concretely: the remote runtime cannot compute undo-history (any local read) without a replicated copy, so the test uses `destroy` (which skips history). **Remaining:** the remote **read** path — the down-channel carries served rows and the runtime serves views from a replicated base (the read-replication §4.3 describes), folded into the coverage/subscription model (W4); and sibling view replicas (detail/conversation).
- **W4 — hardening + config surface.** Coverage/working-set for a split runtime, reconnection/snapshot recovery, and the control-config UI for the per-link transport switch.
- **W5 — one link node across deployments (§4.2).** The client-side link node is the same Rust code everywhere. Browser-WASM already exists (`posthaste-link-wasm`); this slice adds the **Tauri-native** path — run the link node natively in the Tauri Rust process and serve the webview over IPC, retiring the desktop's embedded localhost HTTP server. Parallel to the W0–W4 backend-link arc (it is a client↔runtime *deployment* change), but it lands on the same shared `LinkTransport`, so do it after W0 fixes the contract.

## 7. Assertions

| ID | Sev. | Assertion |
| --- | --- | --- |
| backend-link-is-replication-only | MUST | The runtime reaches the backend only through `BackendLink`'s named-mutation up-channel and base-assertion down-channel; it does not read the backend store across the link — reads are derived locally from the base cache. |
| transport-selected-by-config | MUST | A link's transport (in-process vs remote) is chosen from runtime configuration, not at build time; the default is in-process co-located. |
| colocated-unchanged | MUST | With the default in-process transport, the co-located deployment behaves identically to the pre-link implementation (the seam extraction is behavior-preserving). |
| reuse-link-core | SHOULD | The runtime near node reuses `posthaste-link-core`'s predictor + convergence engine rather than a second bespoke outbox/rebase. |
| one-link-transport | MUST | Both links use one link mechanism: one shared contract/wire and one Rust `LinkTransport` implementation, run natively (Tauri/daemon) or as WASM (browser, `posthaste-link-wasm`). The client does not reimplement the link in TypeScript; browser TS is limited to a dumb I/O shim + the renderer. |
| one-replica | MUST | Both near nodes hold a read-model replica from **one** implementation — `posthaste-link-replica` over the `posthaste-link-core` predictor — run natively (runtime) or as WASM (browser client). The runtime does not hand-write a second replica; the read-model twin of `one-link-transport` (§4.3). |
