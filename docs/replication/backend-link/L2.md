## 1. Component map

- **`BackendApi`** (`posthaste-link-contract`) — the link trait (up/down/read). One contract, two implementations.
- **`LocalBackend`** / **`RemoteBackend`** (`posthaste-authority-runtime/src/transport.rs`) — the in-process and over-HTTP implementations of `BackendApi`.
- **`Backend`** far node (`posthaste-authority-runtime/src/backend.rs`) — the single owner of backend access (the `MailService` + store + `mail_queries`); `LocalBackend` delegates to it.
- **`BackendLink`** handle (`posthaste-link-contract`) — the runtime's typed handle over `Arc<dyn BackendApi>`.
- **`link_router`** (`posthaste-server/src/link.rs`) — the far-node HTTP/SSE surface serving the link wire.
- **`ReadCache`** (`posthaste-authority-runtime/src/read.rs`) — the read-through cache, policy-parameterized.
- **The runtime near node** — `RuntimeBackendOutbox` + `posthaste-link-replica::MailListReplica` folded over served reads.

## 2. BackendApi implementations (LocalBackend, RemoteBackend)

`LocalBackend` calls the co-located `Backend` far node directly — zero serialization, synchronous confirmation; the behavior-preserving default. `RemoteBackend` is a real client: the up-channel `POST`s the named mutation, the down-channel opens an SSE stream and parses `data:` frames into `DownFrame`s (a pure `parse_sse_frame` mapper), and the read channel `POST`s/`GET`s the read endpoints. The wire paths (`LINK_FORWARD_MUTATION_PATH`, `LINK_SUBSCRIBE_PATH`, the read paths) live in `posthaste-link-contract` so client and far node cannot drift.

There is no separate `LinkTransport` trait: the up, down, and read channels are unified on `BackendApi` (`ReadSource` was folded in). A transport override that affects only writes is a composing decorator over a read-capable base.

## 3. The link wire (link_router)

`posthaste-server`'s `link_router(transport)` is the far-node HTTP surface that serves the link endpoints (POST up-channel, SSE down-channel, read endpoints) over any `BackendApi`. A split-backend host mounts it over the backend's in-process `BackendApi` (exposed on `AuthorityRuntimeBuild::backend_link`). The real `RemoteBackend` client and the real `link_router` are proven to meet over loopback HTTP with no mock on either side (`crates/posthaste-server/tests/backend_link_wire.rs`).

## 4. The read-through cache (ReadCache)

`ReadCache` wraps a `BackendApi` read surface with a **policy**:

- **Passthrough** (co-located default) — every read delegates straight through; no storage, no copy, behavior-preserving.
- **Retaining** (remote) — a message-summary cache warmed by both point reads and query pages serves point reads (detail, undo-history) locally. Coherence is the down-channel: a background task evicts a message's entry on any base assertion, so a cached summary is never stale (the next read re-fetches) — not TTL. Mail-list pages are not cached (the authority owns membership/order; a list is a fresh read-through that warms the message cache).

## 5. The runtime near node (read replica + outbox)

The runtime holds a `RuntimeBackendOutbox` of forwarded-but-unconfirmed mutations and folds it over every mail-list recompute through `posthaste-link-replica::MailListReplica` (`apply_outbox_overlay`, `crates/posthaste-authority-runtime/src/near_node.rs`): served rows are the base, the outbox the pending set, the projection the optimistic result. The runtime runs the **same `posthaste-link-replica` crate the WASM client runs**, natively — one replica, two consumers (`one-replica`). A no-op short-circuit when the outbox is empty keeps the in-process default byte-for-byte unchanged.

## 6. Transport selection and config

`BackendTransportConfig` (`InProcess` default | `Remote { base_url }`) is threaded through `RuntimeBuildConfig`; `select_backend_link` builds the `BackendLink` over the config-chosen transport, not at build time (`transport-selected-by-config`). `select_read_source` picks the read path from the same config (`Remote` → read-through, `InProcess` → local). Switching a link to remote is a config change, not a rebuild.

## 7. The build seam and role binaries

`build_authority_runtime` is split so the backend far node and runtime near node compose independently (`backend-builds-standalone`):

- `build_backend(config) -> BackendBuild` — the far node alone, without the runtime.
- `build_runtime(BackendBuild | remote link, config) -> RuntimeHandle` — the runtime over a backend link.

The lean role binaries compose these (`separate-role-binaries`): `posthaste-backend` (far node + `link_router`, no renderer), `posthaste-runtime` (runtime over a remote backend link), `posthaste-daemon` (backend + runtime in-process). The bundled control app composes the daemon + renderer. The first dogfoodable split (backend on one host, runtime on another) is proven.

## 8. Assertions

| ID | Sev. | Assertion |
| --- | --- | --- |
| one-backend-api | MUST | The up, down, and read channels are one trait (`BackendApi`) with `LocalBackend`/`RemoteBackend` implementations; there is no separate transport or read-source trait. |
| one-replica | MUST | Both near nodes hold a read-model replica from one implementation — `posthaste-link-replica` over `posthaste-link-core` — run natively (runtime) or as WASM (browser client); the runtime does not hand-write a second replica. |
| link-wire-shared-paths | MUST | The remote wire paths live in `posthaste-link-contract` so the `RemoteBackend` client and the `link_router` far node cannot drift; they are proven to meet over loopback HTTP with no mock. |
| backend-builds-standalone | MUST | `build_backend` produces the far node without the runtime; `build_runtime` consumes a backend link (local or remote); the two compose independently. |
| separate-role-binaries | MUST | Each deployment role (backend, runtime, daemon) is a thin binary composing only the libraries it needs; a headless install carries no renderer/Tauri/webview code. |
