## 1. Boundary

L4 made the runtime↔backend boundary a real, transport-switchable link, and the
client↔runtime link already exists. This spec makes the three components —
**client**, **runtime**, **backend** — independently *deployable*: each is a thin
binary composing only the shared libraries it needs, the links between them are
selected by configuration, and one default **control app** bundles all three and
lets you choose what to enable and how. It is the topology layer over the L4
mechanism, realizing [L1 §10](L1.md)'s deployment instances as concrete
artifacts (and adding **daemon** — headless runtime+backend — to the bundled /
hosted-runtime / hosted-backend set).

### 1.1 What changes and what does not

- **Does not change:** the link mechanism (L4), the link/replica logic, or the
  default bundled behavior (the control app with the bundled preset is identical
  to today's desktop app).
- **Changes:** the build is factored so the backend far node and the runtime near
  node compose independently; lean per-role binaries are added; the topology
  (which components run, which links are local vs remote) is read from
  configuration; and every remote link surface is authenticated.

## 2. Components, scopes, and links

Three component **scopes**, each with its own settings:

- **backend** — the read-model authority: store + providers + the L4 `Backend`
  far node. Serves the runtime↔backend link.
- **runtime** — the near node: sessions, views, outbox, read-through cache.
  Consumes a backend link (local or remote); serves the client↔runtime link.
- **client** — the renderer. Consumes a runtime link (local or remote).

Two **links** (both L4 contracts, transport-selected): **client↔runtime** and
**runtime↔backend**. A scope's far side is *local* (in-process, co-located) or
*remote* (over the link). The links are the only coupling; nothing else crosses a
scope boundary.

## 3. Binaries: separate thin roles over shared libs

The shared *logic* lives in libraries (the `posthaste-*` crates). Each deployment
**role is its own thin binary** composing only the libs it needs, so a headless
server install carries no renderer/Tauri/webview code (`separate-role-binaries`):

| Binary | Composes | Serves | Renderer |
| --- | --- | --- | --- |
| `posthaste-backend` | backend far node + link server | runtime↔backend link | no |
| `posthaste-runtime` | runtime + remote backend link | client↔runtime link | no |
| `posthaste-daemon` | backend + runtime (in-process) | client↔runtime link | no |
| **control app** (desktop/Tauri) | all three + control pane | local + (optionally) remote | yes |
| client (web) | renderer | — (connects to a runtime) | — (browser) |

The **web client** (`apps/web`, static) is the standalone renderer; a thin Tauri
client-shell (renderer + remote-runtime link, no local runtime) is an optional
variant. The control app is the **default install**.

## 4. The build seam

To compose roles independently, the L4 build is split (today
`build_authority_runtime` builds backend + runtime entangled):

- `build_backend(config) -> Backend` — the far node alone.
- `build_runtime(BackendLink, config) -> AuthorityRuntimeHandle` — the runtime
  over a backend link, in-process (local backend) or remote.

Then: `posthaste-backend` = `build_backend` + serve; `posthaste-runtime` =
`build_runtime(remote link)` + serve clients; `posthaste-daemon` =
`build_backend` + `build_runtime(in-process link)` + serve clients; the control
app = daemon + renderer + control pane. This is "compute at the authority,
runtime over a link" expressed at the build (`backend-builds-standalone`).

## 5. Configuration

A **topology config** selects, per scope and per link, what runs and where:

- Each scope is independently enabled; each link is `local` or `remote { url }`.
- **All combinations are allowed** (`free-combination`); the [L1 §10] deployment
  instances (bundled / hosted-runtime / hosted-backend) plus **daemon** are
  **named presets** over the free config, not the only shapes.
- The lean binaries are **fixed-role**: they read the config subset for their role
  (listen address, link URLs, auth) but do not switch roles.
- **Topology switching lives only in the control app** (`control-is-the-only-switcher`):
  its control pane edits the topology config; the app composes components at
  startup. A change **applies by restart** of the affected components, not live
  hot-swap (`switch-by-restart`).

## 6. Auth on every remote link

A link surface reachable off-box MUST be authenticated (`remote-links-authenticated`).
The runtime↔backend link surface (`link_router`) and the client↔runtime surface
are placed behind the capability-token / `require_auth` machinery (the
`feature/capability-tokens` + `feature/api-platform` work, folded in here). An
in-process link needs no auth (it never leaves the process); a `remote` link
always presents and verifies a credential. No unauthenticated remote link ships.

## 7. Transports: HTTP universal, IPC optional

HTTP(+SSE) is the **universal** link transport (`http-universal-transport`): it is
how a remote or web client reaches a runtime and how a runtime reaches a remote
backend. The Tauri-native IPC node ([L4 §4.2](L4.md) W5) — running the link node
natively in the control app's Rust process with the webview as a pure view —
is an **optional optimization for the bundled case only**, sequenced last; it
never gates the topology, and the control app still serves HTTP when a
remote/web client is configured.

## 8. Slicing

- **W6a — build seam.** *(Landed.)* `build_authority_runtime` is now
  `build_backend(config) -> BackendBuild` + `build_runtime(BackendBuild, config)`;
  the bundled build composes them in order, byte-for-byte the same graph
  (behavior-preserving, all suites pass). The far node builds without the
  runtime; the runtime builds over it.
- **W6b — config wiring + auth.** Topology config → the builds; mount the link
  surfaces behind auth; the dormant L4 remote paths become reachable.
- **W6c — lean binaries.** `posthaste-backend`, `posthaste-runtime`,
  `posthaste-daemon` as thin role binaries; first dogfoodable split (backend on
  one host, runtime on another).
- **W6d — client↔runtime selector.** The client-link transport config (remote
  runtime URL; web vs desktop client), reconciled with `feature/deployment-modes`
  and [[wasm-replica-effort]].
- **W6e — control pane.** The desktop UI editing the topology config: enable/point
  each scope + link, presets as shortcuts, restart-to-apply.
- **W6f — Tauri-native IPC (optional, last).** L4 W5: native link node + webview
  IPC, retiring the embedded localhost HTTP server for the bundled case.
- **W6g — hardening (dogfood-driven).** Cache bounds/LRU, account-scoped
  eviction, reconnect/snapshot recovery, coverage reporting, role-move optimism.

## 9. Deferred: unify the client↔runtime link onto the same contract

The far-node contract here (`BackendApi`, the runtime↔backend link surface) and
the client↔runtime wire are **not** the same trait today, by deliberate choice.
The client↔runtime far node (the runtime) serves a *superset* — sessions, views,
and `RuntimeFrame`s — over the existing `/v1/runtime/*` HTTP/SSE adapter, with
the WASM replica layered on. The two seams share the **vocabulary**
(`MutationRequest`/`MutationReceipt`/frames/assertions) and the **mechanism**
(the `link-core` predictor + `link-replica` cache), but use different trait
objects.

In the fully-realized recursive-cache model they **converge**: sessions become
the client near node's connection/coverage state, views become coverage
subscriptions served down the same channel, and `open_view` becomes
`subscribe(coverage)` + read-through. Stripped of those, the runtime-as-far-node
serves exactly what the backend does, and **one `BackendApi` would contract both
seams**.

**This is tracked, not scheduled.** Realizing it means rewriting the *shipped*
client↔runtime protocol (web + desktop + server `/v1/runtime/*`) from stateful
sessions/views to the replication-link shape — a large, higher-risk effort that
is its own W-arc, not part of the backend-link consolidation. Until then we
accept the asymmetry: `BackendApi` is the runtime↔backend contract; the
client↔runtime keeps its session/view wire. Renaming back to a shared link name
is cheap if we later commit to the unification.

## 10. Assertions

| ID | Sev. | Assertion |
| --- | --- | --- |
| separate-role-binaries | MUST | Each deployment role (backend, runtime, daemon) is a thin binary composing only the libraries it needs; a headless install carries no renderer/Tauri/webview code. |
| backend-builds-standalone | MUST | `build_backend` produces the far node without the runtime; `build_runtime` consumes a backend link (local or remote). The two compose independently. |
| remote-links-authenticated | MUST | Every link surface reachable off the local process is behind authentication; no unauthenticated remote link ships. In-process links need none. |
| http-universal-transport | MUST | HTTP(+SSE) is the universal link transport; IPC is an optional bundled-case optimization that never gates the topology. |
| control-is-the-only-switcher | MUST | Topology switching (enabling components, choosing local vs remote links) lives in the control app; lean binaries are fixed-role. |
| switch-by-restart | SHOULD | A topology change applies by restarting the affected components, not by live hot-swap. |
| colocated-default-unchanged | MUST | The default control install with the bundled preset behaves identically to the pre-L5 desktop app. |
| free-combination | SHOULD | All component/link combinations are allowed; the L1 §10 deployment instances (+ daemon) are presets over the free config. |
