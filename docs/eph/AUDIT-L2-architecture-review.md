## 1. State of the app

This is a clean codebase and the numbers are earned, not cosmetic: 2 TODOs, 0 ignored tests, ~1200 tests including two *required* live-Stalwart CI jobs, and a migration/salvage story (`open_with_repair` quarantining the whole file and salvaging only the op log) that most projects never write down at all. The core designs hold up under adversarial reading — `fold_overlay_row` really is a pure fold over a transaction-consistent snapshot, base writes really are compile-time sealed behind `&BaseWrite`, the supervisor really is a careful state machine with generation tokens and per-arm budgets, and the frontend charter's ratchets (dependency-cruiser, knip and jscpd baselines burned to *zero* with "delete, don't baseline" written into `scripts/check-dead.mjs:12-16`, one invalidation policy) are genuine CI-enforced gates rather than aspirations. The weaknesses are almost entirely at seams, and they cluster into two habits. First: this project repeatedly builds an artifact that *represents* an invariant and then does not wire it up — a drift guard covering 9 of 28 enums, a logging contract CI never runs, a circuit breaker with zero production readers, `RFC-L2-provider-reliability` carrying a `SHIPPED` banner over a decision row that still reads `proposed`, and 647 of 727 `@spec` pointers resolving to nothing. Second: bounds are declared at one layer and defeated at the adjacent one — `derive_overlay(account, message, fold)` reads like a point operation and costs a full account-log read (payloads included) inside the process-global write mutex. Neither is debt in the usual sense; both are the specific residue of moving fast through a large architectural deletion and leaving the enforcement and traceability layers pointed at the previous world.

## 2. Architectural pain points

### 2.1 `derive_overlay` has a per-row signature and an O(whole-account-log-bytes) cost, under the global write mutex

**Problem.** `crates/posthaste-store/src/overlay.rs:121-136` opens `write_transaction` and then selects `{OPERATION_COLUMNS}` — including `payload` — for the *entire* account with no LIMIT and no entity filter; `remove_op_and_derive` (`:185-197`) repeats it and then `ops.clone()`s the Vec per row. `outbox.rs:120,129-131` `serde_json::from_str`s every payload for every row, after which `fold_overlay_row` (`replay.rs:281-294`) discards every op that does not touch the one row. `outbox_operation` has five whole-table-per-account readers and the D67(b) `LIMIT` landed on exactly one of them: `OUTBOX_FLUSH_BATCH_LIMIT = 200` at `outbox.rs:17,241-250`. `list_pending_operations` (`:289`), `list_unsettled_operations` (`:305`), `list_settled_operations` (`:441`) and the derive's inline copy are all unbounded.

**Multipliers.** `coalesce_pending_assertions` (`outbox/queue.rs:318-325`) does a full log read *before* every state-assertion enqueue, so one mutation = two full log reads, one of them under the writer; a burst of N is O(N²) in op-row parses. The per-cycle sweep (`sync_ops.rs:495-500`) chains `list_pending_operations` + `list_unsettled_operations` per tombstone-over-surviving-base row, inline on the async worker. `replay_base_write` (`replay.rs:636-652`) recomputes the inventory per applied sync chunk.

**Concrete consequence.** A failed or parked content op is deliberately kept foldable forever (`replay.rs:197-201` + `CONTENT_KINDS`), truncation only removes `applied` ops, and `SendMessageAttachment.content_base64` has no size cap anywhere in the workspace (the only ceiling is `MAX_BODY_BYTES = 64MB` at `api/mod.rs:61`). So one rejected send with a large attachment makes every *unrelated* mutation, settle, truncate and per-chunk replay in that account re-parse those bytes under the process-wide writer until the user manually discards it. The reachable burst path today is automation (`automation/apply.rs:31-45` enqueues one op per matched message over a whole cycle's accumulated `sync_messages`, drained at 200/cycle) — not UI multi-select, which does not exist (`useEmailActions.ts` is single-target throughout, and `models/src/command/mail.rs` has no multi-id command). That last fact is the real cost: the obvious next features (bulk archive, mark-folder-read) are forced to be N commands, each O(log).

**Why it survived.** `crates/posthaste-bench/src/workloads.rs:287-304` — the workload documented as modelling "the NS1 mutation-path store write" — calls `upsert_overlay_message` directly on a fixture with an empty outbox, bypassing `derive_overlay` entirely. No benchmark in the repo touches the log read.

**Shape of the fix.** Give the derive an entity-scoped snapshot: filter the log read by the row's addressable keys (entity id ∪ resolved alias ∪ send-consumed-draft key) instead of by account, and drop `payload` from the projection for ops the fold cannot use it for. Apply the D67(b) LIMIT idiom to the other four readers or give them explicit pagination. Point the bench at `derive_overlay` on a non-empty outbox so the cost becomes visible. Cap `content_base64`. **Effort: M.**

Related and separable: `ServiceSyncSink` accumulates every `MessageRecord` for the whole cycle (`sync_ops.rs:30,97,211`) although automation needs only ids + a count and cache-candidate scoring is per-chunk-able; and IMAP chunks only `InitialSync|ResumeInitialSync` (`streaming.rs:155-163`), so every other full snapshot — including the non-CONDSTORE `FlagDeltaUnavailable` path — accumulates the whole account into one `SyncBatch` and one write transaction. That is verbatim the shape D94 describes, under a milestone banner reading SHIPPED.

### 2.3 The provider-call breaker is unobservable, and D98 does not exist under a SHIPPED banner

**Problem, part one.** `ProviderCallExecutor` is reached from three call sites, all in `posthaste-engine` (`live_message.rs:176,207` as `CallClass::Blob`; `live_mutation/requests.rs:211` as `CallClass::Metadata`, itself reached from six `live_mutation.rs` sites covering keyword flips and all `Mailbox/set` ops). JMAP sync — `sync/email.rs:148-160` `client.email_changes`, `:162-172` `send_get_email()`, `:262-290` the full-snapshot chunk loop — calls jmap-client directly, so `BreakerRegistry` (threshold 5, `breaker.rs:18`) never observes the dominant traffic class. Worse: `breaker_phase()` (`executor.rs:172`) has **zero production callers** — only tests — so even when the breaker opens, D83/D91's "surfaced as Degraded" has no wiring into `AccountRuntimeOverview`. `ExecutorConfig` is constructed once with `..default()` (`live.rs:243`), so its thresholds are not configurable and are exercised by three call sites.

**Problem, part two.** The poll loop has no failure-aware pacing. `supervisor.rs:1245,1281,1327,1336` all reset to a flat `sync_poll_interval(shared.poll_interval)` (60s, `:42`); `mark_sync_failure` (`:695-717`) writes status strings and returns nothing the loop reads; a failed cycle tears the connection down (`:1563-1565`) and `ensure_connection` (`:1593-1610`) rebuilds it next tick with no cooldown and **no `AuthError` gate**. There is no consecutive-sync-failure counter (the watchdog covers panics/exits only), no startup splay (`lib.rs:202-204` → each account fires `SyncTrigger::Startup` immediately with zero offset), and no cross-account concurrency cap.

**Doc drift is internal to one file.** `docs/eph/RFC-L2-provider-reliability.md:20-29` reads "Status (2026-07-04): SHIPPED... M30–M37 all shipped"; the M36 row (`:257`) lists D98 ("startup jitter + global sync cap") among its contents; the D98 row (`:214`) still reads `proposed`; and §6/O7 (`:297-299`) still asks which limiter to use and what the cap value should be. M36's acceptance gates never included a D98 test, which is how an unimplemented row shipped as landed.

**Concrete consequence.** An account with revoked credentials performs a fresh connect + auth attempt (IMAP TCP+TLS+LOGIN, or an `invalid_grant` OAuth refresh) every 60 seconds forever, with no escalation — the one place the missing pacing has provider-side consequences rather than just wasted radio. And a subsystem with its own crate, config struct and 8 tests guards a minority of calls while reporting to nobody, so the next person tuning `ExecutorConfig` to stop a 429 storm will change values the failing calls never read.

**What to drop from the original framing.** The durable specs are honest: `docs/architecture/L2-crate-topology.md:49` says "Only `engine` depends on it", and `docs/backend/L1-backend.md:44-47` promises per-class deadline + typed classification + the send-uncertain rule — all three of which *do* hold on the bypassing paths via `live.rs:41` (`.timeout(METADATA_TOTAL)`, with a comment naming exactly this bypass), `imap/src/timeout.rs`, `SEND_TOTAL`, and `classify_send_dispatch_error`. Only the ephemeral RFC overstates. The `pub(crate) fn run` argument is a visibility keyword, not a structural barrier — IMAP already consumes the shared policy core (`session.rs:98`, `idle.rs:44` build `BackoffSchedule`). And there are not four forked backoffs: three of four call `BackoffSchedule::delay_for`; only `watchdog_backoff_delay` re-derives the curve, and the ~6-line `jitter_unit()` copies are the policy crate's deliberate injected-randomness design (`call-policy/src/backoff.rs:74-86`), annotated as intentional at `idle.rs:210-211`. The ten-phase-locked-accounts herd is a hypothetical for a desktop client.

**Shape of the fix.** Correct the RFC banner and either implement or explicitly de-scope D98. Add a consecutive-failure counter to the sync arm and gate `ensure_connection` on `AuthError`. Either wire `breaker_phase()` into the runtime overview or delete the breaker. **Effort: M.**

## 3. Judgement calls

### 3.1 The L2-optimism model's two write-discipline violations — real defect or documentation nit?

Both reviewers verified every cited line. They disagree on severity, and the disagreement is worth resolving deliberately.

**The facts neither disputes.** `replay(log, base)` is not total: `fold_overlay_row`'s `Some(None) if snapshot.base.is_some() => Keep` arm (`replay.rs:299-303`) reads the *current overlay*, so an ownerless tombstone is durable state, contradicting `replay.rs:16-17` ("Nothing is a non-derivable pass-through") and `docs/backend/L2-optimism.md:108`. And `outbox/draft.rs:537` is the sole production caller of `tombstone_overlay_message` — an imperative write on the derived plane, paired with a `remove_draft_alias` at `:519` that deliberately destroys the fold input addressing that row. Separately, `coalesce_pending_assertions` deletes superseded ops in one transaction and inserts the merged replacement in another (`queue.rs:337-344` → `queue.rs:283-301`), and `remove_operation_after_local_failure` (`mutation.rs:71-78`) restores nothing.

**The "not real" case.** The claimed harm — destroyed messages and sent-away drafts reappearing — requires the overlay to be wiped while base survives, and no such path exists. `open_with_repair` quarantines the *entire* database file (`store.rs:294-346`, `quarantine_database` at `:779-800`) and salvages only `outbox_operation` + `draft_alias`; the sole production caller of `replay_account_overrides` is `lib.rs:176-189`, guarded on `repair.is_some()` with the comment "starts with an EMPTY overlay". With base empty, a missing tombstone hides nothing. There is no overlay-clearing primitive anywhere in the port. The `Keep` arm is documented twice as a required bridge (without it, truncating a Destroy would flicker deleted mail back into view) and is directly tested (`tests/replay.rs:1306-1402` `settled_destroy_blocks_tombstone_repair`). The reviewer's `op.entity.id == row_id` observation is backwards: the mismatch makes the repair *fire*, enqueueing a `DraftDelete` keyed to that row id, which the fold then owns — self-terminating within one sweep. And coalescing is reachable only under `kind.is_state_assertion()` = `SetKeywords|ReplaceMailboxes|Destroy`; content ops coalesce through the atomic guarded `replace_operation_payload`, so no authored words can be lost. Worst case is one flag toggle lost in a sub-millisecond crash window, and the next sweep re-derives to provider truth.

**The "real, medium" case.** The cost is invariant *precision*, and the proof that it already cost something is in-tree: the v5 migration — the one time overlay surgery happened — had to hand-carve an exception to a rule stated as absolute (`db/schema.rs:344-346`: "Tombstone rows are NOT pins... and are left alone"). The next maintainer who needs a non-additive overlay schema change, or a "distrust the derived view" path, reads "a full rebuild is always legal" and silently drops tombstones. Second, the `draft.rs:537` write plus the deliberate pre-write alias removal is a genuine three-way coupling (fold `SendConsumedDraft` arm, alias-removal timing, imperative tombstone branch) that anyone touching send-consume semantics — undo-after-settle, resend-from-sent — must keep in sync across three places. Third, `coalesce_pending_assertions` calls the *unguarded* `remove_operation` (`store/outbox.rs:474`: `DELETE ... WHERE id = ?1`) on ops read as Pending in an earlier transaction, when a purpose-built `remove_operation_unless_inflight` (`:502`) exists for exactly that race against `claim_operation_for_flush`.

**My read:** the second position is the actionable one and the fixes are all **S**: name the tombstone exception in `replay.rs`'s module doc and in `L2-optimism.md`, and swap `coalesce_pending_assertions` onto the guarded delete. Do not chase the resurrection bug — it isn't there.

### 3.2 Is the production half of the atomic derive tested?

**The narrow fact both agree on:** no test calls `DatabaseStore::derive_overlay` or `remove_op_and_derive` by name; all 79 fold tests run against `TestStore`, whose snapshot is a ~190-line parallel implementation in `service/tests/store_sync_cache_impls.rs`, and the doubles hand-code the replayable predicate (`:409-411`, `:481-483`, plus a third at `store_command_event_impls.rs:154-158`) instead of calling `OperationKind::is_content_op()`.

**Against the finding (persuasive):** the strong claim — "the only real-DatabaseStore exercise is one test at `continuity.rs:403-460`" — is false. `posthaste-testkit/src/harness.rs:23-48` builds a real `DatabaseStore` + real `MailService`, and nine *ungated* tests (`draft_send_consumption.rs` ×4, `gmail_mutations.rs` ×5, against an in-process mock IMAP/SMTP fixture, no env gate, no `#[ignore]`) plus four in `apps/client/backend/tests/api.rs` drive every mutation/settle/flush/truncate through the production derive and assert on rows read through the `message_effective` views. Three of the four named failure modes are pinned by those assertions: `draft_send_consumption.rs:272-340` (resume under the same compose key, exactly one Drafts row) is a tight check on alias-map scoping *and* op ordering, and the row only lands in `messages_in(..., drafts_mailbox)` if the role lookup resolves. Two of the four hypothesized bugs are impossible by construction — the SQL kind list is generated from `OperationKind::CONTENT_KINDS` via `content_op_kinds_in_sql()`, and role values are materialized into `mailbox.role` at write time. Most importantly the drift mechanism is *inverted*: `fold_overlay_row` re-applies `is_replayable` to the snapshot (`replay.rs:281-284`), so both filters are prefilters — over-inclusion is a no-op, under-inclusion fails tests loudly. Adding a content kind leaves the double strictly narrower, so the new test *fails*; it cannot silently report green.

**For the finding (also persuasive, and narrower):** there is exactly one place where the SQL is *authoritative* rather than a prefilter — the `OR kind IN (<CONTENT_KINDS>)` half. If a failed content op never enters the snapshot, the pure fold cannot rescue it and a parked draft or send silently vanishes from the mail list. That clause appears in **three** duplicated query strings (`overlay.rs:127-134`, `:188-195`, `outbox.rs:319-327`) and *no* test exercises the failed-content branch of any copy: the store's only Failed-op test asserts the *exclusion* side (a `Destroy` intent, `tests/outbox.rs:106-145`), and the only two real-store Failed setups are an immediately-retried draft with no list assertion (`api.rs:2610`) and an env-gated `setKeywords` intent (`live_stalwart.rs:826`). The invariant itself is asserted only against the double (`tests/replay.rs:833` `rebuild_reproduces_a_permanently_failed_content_op_row`). A maintainer consolidating those three identical queries — a natural `/simplify` target, and I'd expect it to happen — ships a user-visible regression with the suite green.

**My read:** report it as the narrow version. Two **S** items: add a real-store test that parks a failed `DraftCreate`/`Send` and asserts the derived row survives, and de-duplicate the three query strings behind one function *at the same time* so the consolidation happens with the test in place. Drop the predicate-drift story and the "only one real-store test" claim; both are wrong. Cheap secondary: `upsert_overlay_message` now has zero production callers (bench + doubles only) while `ports/overlay_store.rs:16-20` still documents the retired imperative accept/refold/remove lifecycle as the write path.

## 4. Unverified — surfaced but not adversarially checked

These four came out of synthesis and did **not** go through skeptic verification. Treat the claims as leads, not findings; each cites concrete lines, but nobody tried to refute them.
