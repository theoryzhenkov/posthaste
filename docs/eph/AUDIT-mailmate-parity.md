# AUDIT — MailMate vs Posthaste feature parity

**Date:** 2026-07-07 · **Workspace read:** `.workspaces/scripting-mcp` (synced to main; file:line refs are repo-relative)
**Method:** Posthaste's surface was cataloged by *reading* the code (action registry, compose, config schema, query grammar, store, authority server, MCP/CLI, desktop shell) — not keyword-grepping for feature names. MailMate's feature set was grounded by live web fetches of the manual (`manual.mailmate-app.com`), freron.com, the freron blog/tracker, and github.com/mailmate; the handful of memory-based or weakly-sourced MailMate items are flagged inline and in §4. Every ABSENT claim below lists what was searched.

Two previously-claimed phantom gaps, re-verified as **not gaps**:
- **Unified inbox EXISTS** — default cross-account smart mailboxes (Inbox/Archive/Drafts/Sent/Junk/Trash/All Mail) filtering on `mailbox_role`: `crates/posthaste-config/src/defaults.rs:12-22`.
- **Recipient autocomplete EXISTS** — persistent, frequency-ranked address book harvested from senders *and* recipients of all mail (`crates/posthaste-store/src/sender_cache.rs:5-21`, `address_book` table), wired into compose (`apps/web/src/components/compose-overlay/RecipientSuggestionInput.tsx:1-12`, `apps/web/src/composeAddressSuggestions.ts:30-45`) **and** the rules editor (`apps/web/src/components/settings-panel/rule-group/conditionValueWidgets.tsx:148-161`).

## 2. Posthaste is AHEAD

All evidence-backed; these are differentiators MailMate does not have (or has weaker):

1. **Snooze** — MailMate explicitly lacks it (tracker #605); Posthaste has presets → server scheduler → auto-return-to-Inbox (`supervisor/runtime.rs:386-397`).
2. **Agent scripting: MCP server + CLI from one registry** — 14 operations rendered as both MCP tools and `posthastectl` subcommands (`apps/mcp/src/operations/index.ts:8-17`; `list_accounts`…`trigger_sync` in `read.ts`/`commands.ts`), plus `watch --exec` event streaming (`apps/mcp/src/cli/watch.ts:4-14`) and a built-in localhost webhook receiver `hook serve` (`apps/mcp/src/cli/hook.ts:1-22`). MailMate's bundles are macOS-shell-bound; this is a first-class, cross-platform, agent-facing surface.
3. **Server-side rules with capability-scoped hooks** — event-bus rules whose actions ladder up to webhook/exec under per-invocation attenuated tokens, with a structurally REST-unrepresentable `exec` (config-file-only, `crates/posthaste-domain-model/src/model/rules.rs:76-132,149-182`), central-evaluate/edge-execute `emit` (`rules.rs:91-98`), dead-lettering (`rules.rs:289-300`). Plus ingestion automations with **backfill over existing mail** (`automation.rs:17,25-32`).
4. **Local-first with a shared predictor + durable outbox** — one optimistic-effect fold shared by server and WASM client (`posthaste-replica-core/src/lib.rs:1-15`); user-visible outbox with retry/discard and dispatch-uncertain handling (`OutboxPane.tsx:33-58`).
5. **JMAP native + IMAP** vs IMAP-only (`source_types.rs:26,46`).
6. **Cross-platform** (Tauri; Linux/Windows/macOS targets) vs macOS-only.
7. **Synced, server-authoritative undo/redo history** — a rev-log with a per-account cursor arbitrated by the server (`crates/posthaste-domain-model/src/model/rev_log.rs:4-29`, `apps/web/src/hooks/useUndoRedo.ts:1-11`).
8. **One query grammar across search, smart mailboxes, and rules** (`posthaste-query-grammar/src/lib.rs:1-16`) with regex + relative-date operators (`smart_types.rs:121`, `smart_mailboxes.rs:157-160`) — MailMate has two UIs (toolbar syntax vs condition editor).
9. **Command palette / command search** (`apps/web/src/components/CommandPalette.tsx`, `/` binding `shortcutReferenceRows.ts:52`) — no MailMate equivalent.
10. **Per-tag colors** (`useTagAppearance.ts`) and tag rename/delete migration across carriers (`tagMaintenance.ts:82-95`).
11. **API-first**: REST (`openapi.json`) + SSE event tap (`asyncapi.json`) as supported surfaces.

## 3. Ranked recommendations (gaps most worth closing)

1. **Wire up new-mail OS notifications** *(pre-1.0; arguably a bug)* — the settings toggles exist with no emitter. Add `tauri-plugin-notification`; drive it from the same live inbox counts the dock badge already sums (`useDockBadge.ts`) or from the `message.updated` arrival gate the CLI `watch` uses (`apps/mcp/src/cli/watch.ts:4-14`).
2. **Send-later + undo-send** *(pre-1.0)* — builds directly on the outbox + snooze machinery: give the outbox `send` op a `dispatch_at` honored by the same supervisor tick loop as snooze (`supervisor/runtime.rs:31-35,173-178`); undo-send = a small default delay + the already-existing pending-op discard (`OutboxPane.tsx:53-58`).
3. **Full-text body search + `to:` prefix** *(pre-1.0 for body FTS)* — extend the existing prototype FTS5 index (`fts.rs:4-8`) with body text fed by the body-cache worker (`automation.rs:54-71`); expose `to:` in the grammar (`nodes.rs` — `SmartMailboxField::To` already exists).
4. **List-Unsubscribe (one-click) + reply-to-list** *(pre-1.0)* — parse `List-Unsubscribe`/`List-Id` at ingest into the message projection; a header chip in `MessageDetail` and a `message.unsubscribe` action in the registry (`apps/web/src/actions/defs/message.ts` pattern).
5. **Remote-image blocking toggle** *(pre-1.0, privacy)* — the sanitizer already strips tracking pixels and CSS `url()` (`sanitize.rs:141-163`); add a block-all mode that rewrites `img src` to click-to-load, honoring a per-account/per-mailbox allow.
6. **Custom keybindings** *(post-1.0)* — the action registry already declares chords per action (`message.ts` `shortcut:` fields); a user override map in client preferences (`apps/web/src/client-preferences/`) remaps registry chords without touching dispatch.
7. **Multiple / per-identity signatures** *(post-1.0)* — promote the single per-account signature (`account-editor/state.ts:30-40`) to a list keyed by From option; selection follows the existing identity derivation in `accountFromOptions`.
8. **Thread muting** *(post-1.0)* — a `$muted` keyword + an ingestion-automation action (mark-read/archive on arrival for matching `conversation_id`) — both trigger and action enums are one variant away (`automation.rs:89-120`).

Deliberately *not* ranked: OpenPGP/S-MIME (large, audience decision — flag for a post-1.0 RFC), statistics/thread-arcs/correspondence layouts and auto-submailboxes (niche; the column picker + smart mailboxes cover most of the value), print/mbox export (niche until user demand shows).

## 4. Honesty — what was NOT verified

- **No macOS/Windows runtime here** (Linux jj workspace, no app launched): dock-badge behavior, updater flow, window management, and any Tauri platform quirks are verified only in source, not observed. Cross-platform "ahead" claims are build-config claims.
- **New-mail notification "unwired"** is a *no-emitter-found* claim (searched `newMail` consumers, `tauri-plugin-notification`, `new Notification(` across `apps/` and `crates/`), not a runtime proof; a path I did not recognize could exist.
- **MailMate grounding** came from live fetches by a research subagent (manual.mailmate-app.com — note `manual.mailmate.com` does not resolve; freron.com; blog; tracker; github.com/mailmate). Weak/memory-based MailMate items: format=flowed sending (memory), reply-to-list (2013 tracker ticket only), macOS print/mbox import and Sparkle updater (memory). "Mailbox sets" and a "tag-cloud display" could not be confirmed as real MailMate features and were excluded.
- **Not audited**: `crates/posthaste-server` (appears to be a dev/parity harness vs Stalwart), `posthaste-lab`, `posthaste-bench` internals; the desktop e2e layer; accessibility; localization. Time-boxed out: per-condition operator coverage of the rules *editor UI* vs the schema (schema verified; every editor widget not individually exercised).
- **Search evidence caveat**: `body:`→Preview mapping is from the grammar (`nodes.rs:32-37`) and the FTS index definition (`fts.rs:4-8`); whether some server search path additionally greps cached bodies was not found, and I did not exhaustively trace every search entry point.
